# ПРОМТЕХНОСФЕРА — Финансовая платформа

Многопользовательская платформа управленческого учёта: начисления и движение
денег отдельно, ДДС/ОПиУ/управленческий баланс, дебиторка/кредиторка,
зарплата, интеграции с 1С и Битрикс24, закрытие периодов. Источник истины —
серверная база данных PostgreSQL.

## Стек

- Next.js 16 (App Router) + TypeScript, React 19
- PostgreSQL + Prisma ORM (версионируемые миграции)
- Аутентификация: сессии на подписанных JWT (httpOnly cookie), bcrypt
- Server Actions как серверный API-слой; Route Handlers — для интеграций/экспорта
- Vitest — модульные тесты

## Запуск проекта локально

1. Установите зависимости:

   ```bash
   npm install
   ```

2. Скопируйте `.env.example` в `.env` и укажите строку подключения к
   PostgreSQL и `AUTH_SECRET` (длинная случайная строка).

3. Примените миграции и заполните начальные справочники:

   ```bash
   npm run db:migrate
   npm run db:seed
   ```

   Скрипт `db:seed` создаст роли, права и первого администратора (email
   берётся из `SEED_ADMIN_EMAIL` в `.env`, если не задан — `admin@example.com`).
   Временный пароль будет выведен один раз в консоль.

4. Запустите сервер разработки:

   ```bash
   npm run dev
   ```

   Приложение доступно на http://localhost:3000 и сразу открывает экран входа.

5. Тесты:

   ```bash
   npm test
   ```

## Развёртывание через Docker

Есть `Dockerfile` (многоступенчатая сборка, standalone-режим Next.js) и
`docker-compose.yml` (приложение + PostgreSQL). **Написано, но не
запускалось** в этой среде разработки — Docker здесь не установлен (сборка

хосте). Перед реальным использованием проверьте `docker compose up --build`
на своей машине.

Порядок:

```bash
export AUTH_SECRET=$(openssl rand -base64 32)
docker compose up -d postgres
# примените миграции и заполните справочники с хоста, указав на
# опубликованный порт контейнера (localhost:5432) — сознательно не
# выполняется автоматически при старте контейнера приложения, см. раздел
# «Правила выполнения задачи», п.8 ТЗ
DATABASE_URL="postgresql://promtehnosfera:promtehnosfera@localhost:5432/promtehnosfera" npm run db:migrate
DATABASE_URL="postgresql://promtehnosfera:promtehnosfera@localhost:5432/promtehnosfera" npm run db:seed
docker compose up -d app
```

Обязательные переменные окружения для продакшена: `DATABASE_URL`,
`AUTH_SECRET` (длинная случайная строка — используется и для подписи
сессий, и как ключ шифрования секретов интеграций, см. Этап 7).

## Реализовано (Этап 1: Фундамент)

- Полная схема данных в `prisma/schema.prisma`, покрывающая все домены из
  ТЗ: identity/access, master-data, accruals, cash-management,
  payments-matching, payroll, integrations, reporting, financial-modeling,
  period-close, audit.
- Аутентификация по email/паролю, сессии на JWT в httpOnly cookie.
- RBAC: 8 системных ролей, права настраиваются через
  «Администрирование → Роли и права» (создание ролей, изменение набора
  прав). Пользователи управляются через «Администрирование → Пользователи».
- Разграничение видимости по организациям/подразделениям/проектам
  (`UserOrganizationAccess`, `UserDepartmentAccess`, `UserProjectAccess`,
  `src/lib/access-scope.ts`) подключено к фильтрации данных. Принцип: «явное
  назначение — ограничение» — пока администратор не отметил пользователю ни
  одной организации/подразделения/проекта в «Администрирование →
  Пользователи → [пользователь] → Ограничение видимости», этот разрез
  остаётся неограниченным; полный администратор (`admin.full`) всегда видит
  всё в обход назначений. Подключено к: дашборду, списку документов
  начисления, банку/кассе, сотрудникам, расчётам зарплаты и всем пяти
  отчётам (ДДС, ОПиУ, управленческий баланс, маржинальность, дебиторка и
  кредиторка — включая выпадающий список организаций в фильтрах балансового
  отчёта и отчёта по задолженности). **Не подключено**: выгрузка в Excel
  (`/api/reports/export`), снимки закрытия периода и справочники-выпадашки
  в формах создания документов (создавая начисление, пользователь пока
  может выбрать любую организацию из списочника, а не только «свою») — эти
  места по-прежнему видят данные без ограничения по разрезу.
- Журнал аудита: все создания/изменения/архивирования справочников,
  вход/выход, закрытие и открытие периодов пишутся в `audit_log` и видны в
  «Администрирование → Журнал аудита».
- Учётные периоды: создание, ручное закрытие и повторное открытие с
  фиксацией пользователя и времени. Полный контрольный лист закрытия
  (проверка несопоставленных операций, незакрытых зарплатных расчётов и
  т.д. — раздел 17 ТЗ) — **не реализован**, это Этап 7.
- Справочники с реальным CRUD (создание, редактирование, архивирование —
  без физического удаления) и аудитом изменений:
  организации и ИП, подразделения, ЦФО, проекты, направления, продукты и
  услуги, контрагенты, договоры, статьи ДДС, статьи ОПиУ, статьи баланса.
  Начальные справочники (подразделения, направления, статьи) засеяны по
  тексту ТЗ.
- Дашборд показывает реальные счётчики из базы (организации, подразделения,
  контрагенты, проекты, сотрудники, открытые периоды). Финансовые
  показатели (ДДС, ОПиУ, баланс, маржинальность, точка безубыточности)
  сознательно не выводятся статичными значениями — они появятся на Этапе 3,
  когда будут построены начисления и банковские операции.

## Реализовано (Этап 2: Начисления и деньги)

- Документы начисления (`/accruals`): все 9 типов из ТЗ (счёт, акт, УПД,
  накладная, реализация, поступление, возврат, корректировка, ручное),
  многострочные, с аналитикой (подразделение, ЦФО, проект, продукт/услуга,
  статья ОПиУ) на уровне строки. Жизненный цикл черновик → проведён →
  отменён; редактировать можно только черновик; проведение и отмена
  проверяют, что учётный период открыт.
- Банковские счета и кассы как справочники; операции (`/cash/transactions`)
  вводятся вручную или загружаются из выписки.
- Универсальная загрузка банковской выписки (`/cash/import`): XLSX, XLS,
  CSV, TXT (TXT — автоопределение разделителя), ручное сопоставление
  колонок файла с полями операции (дата; сумма со знаком ИЛИ отдельные
  колонки прихода/расхода; назначение платежа; ИНН и наименование
  контрагента; номер операции банка), защита от повторной загрузки по
  fingerprint (композитный ключ счёт+дата+направление+сумма+назначение,
  либо номер операции банка, если он есть в файле), автоматическое
  определение контрагента по ИНН, протокол импортированных/дублей/ошибок.
  ~~Известное ограничение: без номера операции банка две операции с
  абсолютно одинаковыми счётом/датой/суммой/назначением могут быть
  ошибочно признаны дублем.~~ Исправлено — см. дополнение «Защита от
  дублей выписки без номера операции банка» в конце файла.
- Сопоставление банковских операций с начислениями (`/cash/transactions/[id]`):
  один платёж — один документ, один платёж — несколько документов
  (повторным сопоставлением остатка), несколько платежей — один документ;
  отмена сопоставления. Суммы считаются через `decimal.js`, без ошибок
  плавающей точки. Статусы оплаты документа (не оплачено / частично /
  оплачено / переплата) и сопоставления операции (не сопоставлено /
  частично / сопоставлено) пересчитываются автоматически.
- Дебиторская и кредиторская задолженность (`/reports/debts`): считается из
  проведённых непогашенных документов минус сопоставленные оплаты, с
  выделением просрочки по сроку оплаты.
- Платёжный календарь (`/payment-calendar`): текущий остаток по всем счетам
  и кассам (факт из банковских операций) + прогноз по срокам оплаты
  непогашенных начислений и заявок на оплату; сетка месяца с переносом
  заявок перетаскиванием — см. дополнение «Платёжный календарь: сетка
  месяца и перенос срока оплаты заявок» в конце файла.
- Заявки на оплату (`/payment-requests`) с одноступенчатым согласованием
  (на согласовании → согласована/отклонена → оплачена), не полным
  настраиваемым маршрутом из раздела 9 ТЗ — это упрощение, отмеченное как
  ограничение ниже.
- Дашборд обновлён реальными показателями: остаток денег, дебиторка/
  кредиторка, просрочка, несопоставленные операции, согласованные заявки.

## Реализовано (Этап 3: Управленческая отчётность)

Всё в `src/lib/reports/` — чистые вычисления поверх сохранённых документов
и операций (без статичных цифр), с юнит-тестами на самую рискованную
арифметику (P&L-водопад, точка безубыточности, decimal-суммы).

- **ДДС** (`/reports/cash-flow`) — остаток на начало/конец периода,
  поступления и выплаты по статьям, внутренние переводы отдельной строкой.
  Остаток на начало периода считается как сумма всех операций до начала
  периода (а не через отдельно хранимый остаток на счёте).
- **ОПиУ** (`/reports/pnl`) — выручка → валовая прибыль → операционная
  прибыль → чистая прибыль по методу начисления, с разбивкой по статьям и
  сравнением с предыдущим месяцем. Считается только из проведённых
  документов.
- **Управленческий баланс** (`/reports/balance`) — денежные средства и
  задолженность из фактических данных; авансы, зарплата к выплате, займы,
  капитал и прочие активы — см. дополнение «Управленческий баланс: авансы,
  займы, капитал и остатки» в конце файла (изначально были равны нулю).
  **Контрольное равенство**: «Активы − Обязательства» сверяется с
  накопленной чистой прибылью по ОПиУ, расхождение показывается как
  диагностика с объяснением вероятной причины, а не скрывается.
- **Маржинальность и точка безубыточности** (`/reports/margin`) — валовая
  прибыль, точка безубыточности (Постоянные затраты / Доля маржинального
  дохода), запас финансовой прочности, разбивка по проектам, продуктам/
  услугам и клиентам. Распределение косвенных расходов по этим разрезам —
  настраиваемый драйвер, см. дополнение после Этапа 7 ниже.
- **Фильтры**: период (год/месяц), организация, подразделение, ЦФО,
  проект, продукт/услуга, контрагент — на каждом отчёте.
- **Расшифровка до документа**: клик по статье в ДДС/ОПиУ открывает список
  операций/документов, отфильтрованный именно по этой статье и периоду.
- **Excel-экспорт** (`/api/reports/export`) — ДДС, ОПиУ, задолженность,
  управленческий баланс. Экспорт применяет то же ограничение видимости по
  организациям/подразделениям/проектам, что и сами отчёты на экране.
- Дашборд дополнен показателями текущего месяца: выручка, валовая/
  операционная/чистая прибыль, рентабельность.

## Реализовано (Этап 4: Интеграции)

- **1С — файловый обмен** (`/integrations/1c`): импорт документов начисления
  из табличной выгрузки (XLSX/CSV/TXT — XML/JSON из ТЗ не поддержаны, см.
  ограничение ниже), ручное сопоставление колонок, шаблон файла для
  скачивания. **Идемпотентно**: строка с уже известным внешним ID 1С
  обновляет существующий документ, а не создаёт дубль — проверено
  сценарием «импорт → повторный импорт того же файла → импорт с изменённой
  суммой» с автоматической сверкой количества документов и итоговой суммы.
  Организация ищется по ИНН (создать нельзя — ошибка, если не найдена);
  контрагент ищется по ИНН и автоматически создаётся, если не найден
  (с пометкой `dataSource: "1C"`). Строка с датой в закрытом периоде или
  несуществующей организацией/статьёй не прерывает импорт — уходит в
  очередь ошибок с понятным сообщением, видна в журнале синхронизации
  (`/integrations/1c/batches/[id]`) вместе со счётчиками создано/
  обновлено/ошибок. Прямой обмен через HTTP/OData — не реализован
  (нет адреса публикации и учётных данных), как и требует ТЗ.
- **Битрикс24 — outbox** (`/integrations/bitrix24`): при каждом изменении
  статуса оплаты проведённого документа начисления (сопоставление платежа
  или отмена сопоставления) в очередь идемпотентно ставится событие
  `payment_status_changed` с суммой задолженности и признаком просрочки.
  idempotencyKey включает сумму сопоставления, поэтому повтор с тем же
  состоянием не создаёт дубль в очереди — проверено вручную. Ручная
  отправка через настраиваемый вебхук с журналом попыток и ошибок;
  без включённого профиля событие остаётся в очереди со статусом
  «Ожидает отправки», попытки не растрачиваются впустую. Реальная отправка
  проверена на неотвечающем URL: статус корректно переходит в «Ошибка»,
  попытка и текст ошибки записываются.

## Реализовано (Этап 6: Финансовое моделирование)

- **Сценарии** (`/financial-model`): базовый/оптимистичный/пессимистичный/
  пользовательский, любое количество. Прогноз строится на 12 месяцев от
  выбранного старта (по умолчанию — текущий месяц), стартовая точка
  остатка денег — реальный фактический остаток по банковским/кассовым
  операциям на сегодня (не выдуманное число).
- **Драйверы**: средний чек, количество продаж, сезонность, корректировка
  базовой выручки (изначально — «активация новых услуг»; новые услуги
  теперь задаются списком, см. дополнение «Новые услуги в финансовых
  сценариях»), доля продаж через посредников и их комиссия, переменные
  расходы (% от выручки), постоянные расходы, средняя стоимость
  сотрудника в месяц, платежи по кредитам/лизингу/отсрочкам — все
  редактируются помесячно в одной таблице-редакторе. Пустая ячейка
  означает «не задано», а не 0: для сезонности и корректировки выручки
  это трактуется как 100% (по умолчанию не искажает прогноз), для
  остальных драйверов — как 0.
- **Производительность на сотрудника отдельно по подразделениям**
  (обязательное требование ТЗ, минимум для отдела обучения и охраны
  труда — эти два подразделения подставляются в редактор по названию,
  если их переименовали — берутся первые доступные): для каждого
  подразделения задаются продажи и производительность на сотрудника,
  система считает **требуемую численность = продажи / производительность
  (с округлением вверх)** и суммирует с вручную заданной численностью
  прочего персонала.
- **Прогноз**: выручка → переменные расходы → комиссия посредников →
  валовая прибыль → постоянные расходы + ФОТ → операционная прибыль,
  точка безубыточности и запас финансовой прочности (переиспользуют
  формулы Этапа 3), остаток денег помесячно нарастающим итогом с учётом
  платежей по кредитам.
- **Сравнение сценариев** (`/financial-model/compare`): любое количество
  сценариев бок о бок — выручка, операционная прибыль, остаток денег на
  конец горизонта, средняя точка безубыточности за 12 месяцев.

Проверено сквозным сценарием через реальный UI (не напрямую через БД):
создал сценарий → ввёл средний чек 1000, продажи 100, переменные 30%,
постоянные 20 000, продажи/производительность по двум подразделениям
(55/20 и 40/20) → сохранил → прогноз показал ровно то, что предсказывает
формула: выручка 100 000, численность 5 (3+2, округление вверх),
операционная прибыль −25 000, точка безубыточности 135 714,29, запас
прочности −35,71% — до копейки. Сравнение двух сценариев отобразило
правильные значения бок о бок. Тестовые данные удалены.

При проверке через браузер нашёл и исправил баг в самом тестовом
сценарии использования (не в приложении): `document.querySelector('form')`
в моём тестовом JS-скрипте попадал на форму выхода из системы в шапке
(она в DOM раньше формы страницы) и разлогинивал сессию вместо создания
сценария — после уточнения селектора (`input.closest('form')`) всё
заработало. Также обнаружил и исправил реальный баг в схеме: Prisma не
поддерживает `null` в составном уникальном ключе (`FinancialScenarioValue`
на `[scenarioId, year, month, driver, dimension]`) — заменил
`dimension String?` на `dimension String @default("")` с пустой строкой
как сентинел для «без подразделения» (миграция
`financial_scenario_dimension_default`).

## Реализовано (Этап 7: Закрытие месяца и production-готовность)

### Контрольный лист закрытия периода

`/admin/periods/[id]/close` — все 9 проверок из раздела 17 ТЗ, реально
запрашивают базу (не заглушки):

1. Необработанные документы 1С (импорты с ошибками) — **критично**
2. Ошибки и конфликты интеграций — **критично**
3. Документы без обязательной аналитики (строка начисления без статьи
   ОПиУ) — **критично**
4. Несопоставленные банковские операции за период — предупреждение
5. Незавершённые зарплатные расчёты за период (не «утверждён»/«выплачен»)
   — **критично**
6. Несогласованные заявки на оплату со сроком в периоде — предупреждение
7. Расхождения управленческого баланса (контрольное равенство из Этапа 3)
   — предупреждение
8. Непроведённые (черновик) документы начисления за период —
   предупреждение
9. Дубли банковских операций по отпечатку — предупреждение (структурно
   не должно случаться, т.к. защищено уникальным индексом при загрузке)

Критические ошибки **блокируют** закрытие — кнопки «Закрыть период» нет,
пока они не исправлены. Предупреждения требуют явной галочки «Я
ознакомился и осознанно закрываю период». Результаты каждой проверки
сохраняются в `period_close_checks` при каждой попытке закрытия (даже
неудачной) — это часть истории периода, видна в списке периодов рядом с
датой закрытия.

При успешном закрытии фиксируется **снимок контрольных показателей**
(`AccountingPeriod.closingSnapshot`): остаток денег на начало/конец
периода, выручка, чистая прибыль, дебиторка, кредиторка, активы,
обязательства, расхождение баланса — на момент закрытия, не
пересчитывается задним числом при последующих изменениях. Показан в
списке периодов по клику.

Закрытый период запрещает изменение документов везде, где это уже было
реализовано на предыдущих этапах (`assertPeriodOpenForDate` в
начислениях, банковских операциях, зарплате) — проверено вживую: критичная
ошибка (незавершённый расчёт зарплаты) корректно заблокировала закрытие
периода без кнопки закрытия.

### Безопасность

Заказал отдельный агентский аудит безопасности по чек-листу раздела 22 ТЗ
(RBAC на каждом действии, SQL-инъекции, XSS, CSRF, секреты в коде,
безопасность загрузки файлов, утечка технических деталей в ошибках,
конфигурация cookie). Нашлось два реальных замечания, оба исправлены:

- **Временный пароль передавался в query-параметре URL** при создании
  пользователя/сбросе пароля — оседал в логах доступа, истории браузера,
  заголовке Referer. Заменено на одноразовую httpOnly-куку
  (`src/lib/flash.ts`, TTL 60 секунд), пароль в URL больше не попадает.
- **Вебхук Битрикс24 хранился в БД открытым текстом** (в его URL зашит
  токен доступа) — теперь шифруется AES-256-GCM с ключом, производным от
  `AUTH_SECRET` (`src/lib/crypto/secret-box.ts`), в форме показывается
  только маска (первые 8 и последние 4 символа).

Остальные пункты чек-листа (RBAC на каждом действии, безопасность
загрузки файлов, отсутствие сырых SQL-конкатенаций, отсутствие секретов в
репозитории, конфигурация cookie, отсутствие `dangerouslySetInnerHTML`)
прошли проверку без замечаний — подробности в истории коммита.

## Дополнение после Этапа 7: настраиваемый многошаговый маршрут согласования заявок на оплату

- Маршрут — упорядоченный список шагов, каждый шаг требует согласования от

  заявки и хранится на ней (`routeId`) — правки маршрута после создания

  списка шагов существующего маршрута повлияют на заявки, уже идущие по
  нему** (шаг может исчезнуть или роль — измениться), это явно
  зафиксировано как ограничение на странице редактирования маршрута.

  системе. Заявка без маршрута по-прежнему требует общего права.

## Дополнение после Этапа 7: автопроводка начисленной зарплаты в ОПиУ

При утверждении расчёта зарплаты (кнопка «Утвердить», переход
`CALCULATED → APPROVED`) система теперь автоматически создаёт и сразу
проводит документ начисления (расход) на сумму начислено + страховые
взносы по каждой строке расчёта, чья статья начисления привязана к
статье ОПиУ (справочник «Виды начислений зарплаты» — поле «Статья
расходов», было в схеме с самого начала, но раньше ничего не читало эту
связь). Закрывает пункт из раздела «Кадры и зарплата» — модуль зарплаты
был отдельным от начислений.

- Документу нужен контрагент (обязательное поле схемы), а сотрудники —
  не контрагенты; заведена единственная синтетическая запись-клиринг
  «Сотрудники (ФОТ)», общая на всю систему, переиспользуемая для всех
  организаций и расчётов.
- Начисленная сумма и страховые взносы относятся на одну и ту же статью
  ОПиУ вида начисления — отдельной статьи «страховые взносы» в этой
  версии нет, оба вида затрат считаются частью «Расходы на оплату
  труда» (сознательное упрощение).
- Идемпотентно: связь документа с расчётом — через `(sourceSystem,
  externalId) = ("payroll", payrollRunId)`, повторное утверждение (если
  бы оно было возможно) не создаст второй документ.
- Строки расчёта без привязанной статьи ОПиУ пропускаются — по ним, как
  и раньше, начисление остаётся ручным; если ни одна строка не
  привязана, документ вообще не создаётся, и страница расчёта явно
  объясняет, почему.
- ДДС отдельно ничего не автоматизирует — как только фактическая
  выплата зарплаты будет сопоставлена с банковской операцией (обычный
  механизм сопоставления платежей, тот же, что для любого документа
  начисления), она попадёт в ДДС сама, без дополнительного кода.
- Чистая логика построения строк — `src/lib/payroll/post-to-accrual.ts`
  (`buildPayrollAccrualLines`), 5 юнит-тестов.
- Проверено сквозным сценарием: сотрудник с окладом 100 000 ₽ → аванс
  50 000 ₽ (НДФЛ 6 500, взносы 15 100) → рассчитан → утверждён →
  автоматически создан и проведён документ «Ручное начисление» на
  65 100 ₽ (= 50 000 + 15 100) с контрагентом «Сотрудники (ФОТ)» →
  отчёт ОПиУ немедленно показал эту сумму по статье «Расходы на оплату
  труда» и уменьшил прибыль на ту же сумму.

## Дополнение после Этапа 7: настраиваемый драйвер косвенных расходов в маржинальности

Раньше страница «Маржинальность и ТБУ» заявляла, что косвенные расходы

  затраты в этом разрезе.
- Проверено в браузере на проведённых документах: проект A (выручка
  200 000, прямые затраты 50 000), проект B (выручка 100 000), косвенные

  прибыль при любом драйвере — 190 000. Драйвер переключается через
  выпадающий список в фильтре, на остальных отчётах этого поля нет.

## Дополнение после Этапа 7: защита от дублей выписки без номера операции банка

Если в выписке нет номера операции банка, строка опознаётся по счёту,
дате, направлению, сумме и назначению платежа. Раньше две настоящие, но
одинаковые операции (например, две комиссии по 150 ₽ за перевод в один
день) давали один и тот же отпечаток — вторая молча считалась дублем и
терялась. Теперь отпечатки считаются по всему файлу сразу, и одинаковые
строки нумеруются в порядке появления:

- первая получает прежний отпечаток — поэтому уже загруженные ранее
  операции и операции, введённые вручную, по-прежнему опознаются как
  дубли; вторая — отпечаток с пометкой «#2», третья — «#3» и т.д.;
- повторная загрузка того же файла даёт те же номера — все строки
  отсекаются как дубли;
- выписка, перекрывающая уже загруженную (например, сначала выписка за
  часть дня, потом за весь день), тоже обрабатывается верно: известные
  операции отсекаются, новые одинаковые загружаются, порядок остальных
  строк в файле не важен;
- строки с номером операции банка не нумеруются: один номер дважды — это
  одна и та же операция.

Протокол загрузки сообщает, сколько строк загружено как повторы уже
встречавшейся в файле операции. Чистая логика —
`computeStatementFingerprints` (`src/lib/bank-import/fingerprint.ts`),
6 юнит-тестов.

Проверено в браузере: выписка с двумя одинаковыми комиссиями и платежом →
загружено 3 (раньше было бы 2 и «1 дубль»); та же выписка повторно →
0 загружено, 3 дубля; выписка за полный день с третьей такой же комиссией
и новой арендой (в другом порядке строк) → 2 загружено, 3 дубля. В базе —
ровно 3 комиссии, платёж и аренда, даты верные.

- **Ограничение**: нумерация опирается на то, что каждая выписка содержит
  день целиком или его начало. Если загрузить сначала выписку, где из двух
  одинаковых операций дня есть только вторая (банк выгрузил день не с
  начала), а затем полную — первая из них будет признана дублем. На
  практике банки выгружают выписки целыми днями.
- Ручной ввод операции (`/cash/transactions/new`) по-прежнему не даёт
  ввести вторую полностью одинаковую операцию в тот же день на тот же
  счёт — там это защита от двойного нажатия; при необходимости достаточно
  чуть изменить назначение платежа.

## Дополнение после Этапа 7: бюджет и план-факт в ДДС и ОПиУ

Новый раздел «Моделирование → Бюджет (план)» (`/budget`) — помесячный план
по статьям: бюджет движения денежных средств (БДДС, статьи ДДС) и бюджет
доходов и расходов (БДР, статьи ОПиУ). Финансовые сценарии Этапа 6 для
этого не подходят: они считают прогноз из драйверов (средний чек, доля
переменных расходов и т.д.), а не по статьям, и сравнить их построчно с
отчётами нельзя.

- **Редактор** — сетка «статья × 12 месяцев» на выбранный год, с итогами по
  разделам и за год. План задаётся либо по компании в целом, либо по
  конкретной организации. Суммы положительные (направление определяет
  статья); пустая ячейка — «плана нет», 0 — «запланирован ноль». Статьи
  переводов между своими счетами в бюджет не входят. Архивные статьи
  показываются, только если по ним уже есть план. Сохранение — вся сетка
  года одной транзакцией, с записью в журнал аудита; неверная сумма
  отсекается ещё в браузере, а на сервере — повторно, и тогда не
  сохраняется ничего. Права: просмотр — `financial_model.view`,
  изменение — `financial_model.manage` (те же, что у сценариев);
  пользователь с доступом только к части организаций видит и правит план
  только своих организаций.
- **ДДС** (`/reports/cash-flow`): при наличии плана на месяц в таблицах
  поступлений и выплат появляются колонки «План», «Отклонение» (факт −
  план) и «Исполнение», строка «Итого» и плановые суммы в карточках.
- **ОПиУ** (`/reports/pnl`): в фильтре «Сравнить с» — предыдущим месяцем
  (как раньше, по умолчанию) или планом. В режиме плана — те же колонки по
  статьям и разделам, плюс строки валовой, операционной и чистой прибыли
  по плану.
- Статья, по которой есть план, но нет факта, всё равно показывается —
  с нулевым фактом, иначе невыполненный план было бы не видно.
- Отклонение подсвечивается по смыслу, а не по знаку: зелёным — в пользу
  компании (больше поступлений и доходов, меньше выплат и расходов),
  красным — нет.
- Какой план берётся: без фильтра по организации — план компании в целом
  плюс планы всех организаций; с фильтром — только план этой организации;
  при доступе, ограниченном частью организаций, — только их планы. При
  фильтре по подразделению, ЦФО, проекту, продукту или контрагенту (и при
  доступе, ограниченном подразделениями/проектами) сравнение с планом не
  показывается, и отчёт объясняет почему: факт в этом случае — лишь часть
  статьи, а план задан на статью целиком.

## Дополнение после Этапа 7: отпускные и больничные по среднему заработку

На странице расчёта зарплаты (черновик или рассчитанный) появился блок
«Отпускные и больничные по среднему заработку»: выбрать сотрудника, дату
начала, число календарных дней — система показывает подробную расшифровку
и по кнопке добавляет строку «Отпускные» или «Больничные» в расчёт (с

автоматического расчёта). Сумма при добавлении пересчитывается на
сервере заново — из формы берутся только параметры. Каждая такая строка
пишется в журнал аудита вместе с расшифровкой (средний дневной заработок,
дни расчётного периода и т.д.).

- **Откуда берётся заработок**: только утверждённые и выплаченные
  расчёты — черновики ещё могут измениться. Заработок относится к месяцу,
  за который начислен: окончательный расчёт 10-го — к предыдущему месяцу,
  аванс и разовые выплаты — к месяцу выплаты.
- **Отпускные** (ст. 139 ТК РФ, Положение № 922): начисления видов с
  отметкой «учитывается в среднем заработке» за 12 календарных месяцев

  командировок по табелю. Средний дневной заработок × дни отпуска. Если в
  расчётном периоде нет ни заработка, ни отработанных дней, — по окладу
  (оклад / 29,3).

  за два календарных года перед годом болезни, плюс заработок у других

  предельной базы. Сумма / 730, но не меньше МРОТ × 24 / 730; × 60/80/100%

  работодателей в системе нет). В расчёт попадают первые 3 дня — их платит
  работодатель; остальное Социальный фонд выплачивает напрямую, это

  добавляются там же. Если нужного года нет, расчёт прямо об этом говорит.

## Дополнение после Этапа 7: оклад и аванс по табелю и производственному календарю

Автоматический расчёт зарплаты больше не платит фиксированную долю оклада:

- **Оклад за месяц** (окончательный расчёт 10-го числа) = оклад ×
  отработанные рабочие дни / норма рабочих дней месяца; к выплате — минус
  аванс, выплаченный 25-го.
- **Аванс** (25-го числа) = оклад × отработанные рабочие дни с 1 по 15
  число / норма рабочих дней месяца — ст. 136 ТК РФ требует платить аванс
  за фактически отработанное время. В месяце без отсутствий это примерно
  половина оклада (в сентябре 2026 — ровно 11 из 22 дней), а не всегда
  ровно 50%.
- **Табель ведётся «по отклонениям»**: рабочий день без отметки считается
  отработанным (пустой табель — полный оклад, как раньше). Не отработан —
  день с отметкой «Отпуск», «Больничный», «Командировка» или «Отсутствие»,
  если в тот же день нет отметки о работе. Отпуск и больничный оплачиваются
  отдельно по среднему заработку (см. предыдущее дополнение). Дни до приёма
  и после увольнения не оплачиваются.
- **Норма рабочих дней** — по новому справочнику «Производственный
  календарь» (`/master-data/production-calendar`): хранятся только
  отклонения от пятидневки (нерабочие будние дни — праздники и переносы, и
  рабочие субботы). Календарь на 2025 и 2026 годы заполнен миграцией; нормы,
  которые из него следуют, сверены с официальными в юнит-тестах: 247
  рабочих дней в 2025 и в 2026 году, январь 2026 — 15, май 2026 — 19,
  ноябрь 2025 — 19 (с рабочей субботой 1 ноября). Если календарь на год не
  заполнен, расчёт не выполняется и говорит об этом прямо — старые строки
  расчёта при этом не удаляются.
- Каждая автоматическая строка показывает, как получена сумма: «Отработано
  17 из 22 раб. дн. месяца (отпуск 5); оклад за месяц 85000.00 минус аванс
  45000.00». Строки отпускных и больничных по среднему заработку — тоже
  (средний дневной × дни). Новое поле `PayrollLine.comment` (миграция
  `production_calendar_and_line_comment`).
- Массовое заполнение табеля с галочкой «Пропускать выходные и праздники»
  теперь пропускает и праздники по производственному календарю.
- **Исправлена ошибка табеля**: массовое заполнение без проекта (обычный
  случай — отпуск, больничный, рабочие дни) падало с ошибкой 500: код
  использовал `upsert` по составному ключу с `projectId`, а Prisma не
  принимает в нём `null` (та же проблема, что с `FinancialScenarioValue`
  на Этапе 6). Заменено на «найти — обновить или создать».
- Чистая логика — `src/lib/payroll/work-calendar.ts`, 7 юнит-тестов.

## Дополнение после Этапа 7: новые услуги в финансовых сценариях

Раздел 15 ТЗ хочет новые услуги списком с датой запуска, а драйвер
«активация новых услуг» был одним общим множителем на выручку. Теперь в
каждом сценарии есть блок «Новые услуги» (`/financial-model/[id]`):

- Услуга: название (или выбор из справочника «Продукты и услуги» —
  тогда название берётся оттуда), месяц запуска, средний чек, продажи в
  месяц на полной мощности, за сколько месяцев услуга выходит на полную
  мощность (0 — сразу) и, при необходимости, свои переменные расходы в %.
- С месяца запуска услуга добавляет к выручке: средний чек × продажи ×
  доля выхода на мощность × сезонность сценария. Выход на мощность —
  линейный: при 3 месяцах — 1/3 объёма в месяц запуска, 2/3 во втором,
  полный объём с третьего. Переменные расходы — свой % услуги или % сценария;
  комиссия посредников считается со всей выручки, включая новые услуги.
- В прогнозе выручка разложена на базовую (драйверы) и по каждой новой
  услуге; то же — в выгрузке прогноза в Excel. В сравнении сценариев
  добавлена строка «в т.ч. новые услуги».
- Прежний драйвер оставлен и переименован в «Корректировку базовой
  выручки»: это тот же множитель, поэтому у существующих сценариев цифры
  не меняются, но он больше не выдаёт себя за «новые услуги» и на новые
  услуги не влияет.
- Добавление и удаление услуг пишется в журнал аудита. Таблица
  `FinancialScenarioNewService` (миграция `scenario_new_services`).
- Попутно: страница сравнения сценариев брала стартовый остаток денег
  собственной копией расчёта без учёта ограничения видимости по
  организациям — теперь использует общий `getCurrentCashBalance(scope)`, как
  страница сценария.
- Чистая логика — `projectScenario`/`rampShare`
  (`src/lib/financial-model/project.ts`) и проверка формы
  (`src/lib/financial-model/new-services.ts`), 8 новых юнит-тестов.

Проверено через интерфейс: сценарий с базовой выручкой 200 000 в месяц

## Дополнение после Этапа 7: автоматическое резервное копирование

Раньше была только ручная команда в README. Теперь:

- **`npm run db:backup`** (`scripts/backup.mjs`, работает на Windows и Linux):
  `pg_dump` в сжатом формате custom во временный файл с переименованием
  после успеха (незавершённая копия никогда не выглядит готовой); проверка,
  что архив читается и в нём есть таблицы (`pg_restore --list`); ротация —
  хранятся `BACKUP_KEEP` последних копий (по умолчанию 14), удаляются только
  файлы копий этой базы, ручные файлы в папке не трогаются. Пароль передаётся
  через `PGPASSWORD`, а не в командной строке. На Windows `pg_dump`
  находится сам в `C:\Program Files\PostgreSQL\<версия>\bin` (или
  `PG_BIN_DIR`).
- **`npm run db:backup:verify`** — то же плюс настоящее пробное
  восстановление: копия разворачивается во временную базу
  `<имя>_restore_check`, число строк сверяется по всем таблицам, временная
  база удаляется. Только так можно знать, что из копии действительно
  восстановимся.
- **Журнал**: каждый запуск пишется в таблицу `backup_runs` (миграция
  `backup_runs`) и строкой в `backups/backup.log` — последнее работает
  и когда сама база недоступна. Код выхода 1 при ошибке — планировщик видит
  сбой. Сообщения PostgreSQL выводятся по-английски: на Windows локализованные
  сообщения приходят в кодировке ANSI и превращались в «кракозябры».
- **Страница «Администрирование → Резервные копии»** (только полный
  администратор): когда была последняя успешная копия, история запусков
  (размер, число таблиц, результат пробного восстановления, ошибки) и
  предупреждение, если успешной копии нет дольше 26 часов.
- **`/api/health`** теперь сообщает свежесть копии
  (`backup: { state: ok | stale | never }`) — внешний монитор может
  предупредить о пропущенном бэкапе. Сам ответ при этом остаётся 200: приложение
  работает.
- **Расписание**:
  - Windows — `powershell -ExecutionPolicy Bypass -File scripts\register-backup-task.ps1`
    регистрирует ежедневную задачу в Планировщике заданий (по умолчанию 03:00,
    `-Time 23:30` — другое время, `-Remove` — удалить); если компьютер
    был выключен, копия делается при следующем включении. Задача запускает
    `scripts\run-backup.cmd` (копия с пробным восстановлением, вывод — в
    `backups\scheduler.log`).
  - Linux — строка в crontab: `0 3 * * * cd /путь/к/проекту && npm run db:backup:verify`.
  - Docker — сервис `backup` в `docker-compose.yml` (`Dockerfile.backup`:
    Node + клиент PostgreSQL 17, копии в томе `backups`, раз в сутки).
    **Написано, но не собиралось** — Docker в этой среде не установлен, как и
    для основного образа.
- **Безопасность**: папка `backups/` добавлена в `.gitignore` и
  `.dockerignore` — копии содержат персональные данные и не должны попасть ни
  в репозиторий (он публичный), ни в образ контейнера.
- Восстановление (затирает текущие данные — сначала остановите приложение):
  `pg_restore --clean --if-exists --no-owner --dbname promtehnosfera backups/<файл>.dump`.
  Безопаснее восстановить в новую базу, проверить и переключить на неё
  `DATABASE_URL`.
- Чистая логика — `scripts/backup-core.mjs` (разбор `DATABASE_URL`, имя
  файла, выбор копий на удаление, сверка строк) и `src/lib/backup/status.ts`
  (свежесть), 8 юнит-тестов.

Проверено на этой машине (PostgreSQL 17): копия 155 КБ, 61 таблица;
пробное восстановление — 61 таблица, 288 строк, совпадает с базой,
временная база удалена; при `BACKUP_KEEP=2` удалена ровно одна старая
копия, ручной файл в папке остался; ненайденный `pg_dump` и недоступная
база — код выхода 1, понятная запись в журнале; обёртка для Планировщика

последней копии (30 ч) — предупреждение, и `/api/health` вернул `stale`.

- **Сделано на этой машине**: задача «PROMTEHNOSFERA backup» зарегистрирована
  в Планировщике (ежедневно в 03:00), пробный запуск через Планировщик прошёл
  успешно.

  в другом месте, см. дополнение «Резервные копии: вторая копия в другом

## Дополнение после Этапа 7: управленческий баланс — авансы, займы, капитал и остатки

Раньше в балансе авансы, зарплата к выплате, займы, капитал и прочие
активы были жёстко равны нулю, поэтому контрольное равенство почти всегда
показывало расхождение. Теперь:

- **Авансы** считаются сами: платёж контрагенту, не сопоставленный с
  документами начисления, — аванс выданный (актив); такое же поступление —
  аванс полученный (обязательство). Не авансы: переводы между своими
  счетами, операции без контрагента и операции по статьям ДДС, привязанным
  к статье баланса.
- **Налоги и зарплата к выплате** — непогашенная часть документов
  автопроводки расчётов зарплаты, отдельно от обычной кредиторки.
- **Займы, капитал, прочие активы** и любые свои статьи баланса:
  - статью ДДС можно привязать к статье баланса (справочник «Статьи ДДС»,
    поле «Статья баланса»): получение кредита увеличивает «Займы и
    кредиты», погашение — уменьшает; взнос учредителя — «Капитал»; покупка
    оборудования — «Прочие активы» (за актив деньги платят, поэтому выплата
    его увеличивает);
  - **балансовые операции** на странице баланса — ручной ввод остатков на
    начало учёта и корректировок (сумма со знаком, дата, организация или
    вся компания, комментарий), с удалением; закрытый период их не
    принимает, всё пишется в журнал аудита.
- Строки, которые баланс считает из операций (деньги, дебиторка, авансы,
  кредиторка, зарплата к выплате), помечены в справочнике статей баланса
  системным кодом — по ним нельзя вводить операции и привязывать статьи ДДС,
  иначе суммы задвоятся. Нераспределённая прибыль считается по ОПиУ, но
  принимает операции — для прибыли прошлых лет на начало учёта.
- Контрольное равенство осталось диагностикой, но теперь указывает на
  реальные пробелы — деньги, прошедшие мимо и документов, и статей баланса
  (комиссия банка без документа, неучтённый остаток и т.п.); подсказка на

## Дополнение после Этапа 7: 1С — многострочные документы

Раньше каждая строка файла 1С становилась отдельным документом с одной
строкой начисления, а один акт или УПД с несколькими позициями загрузить
было нельзя. Теперь:

- **Строки с одинаковым внешним ID 1С — один документ**, каждая строка
  файла — строка начисления со своей суммой, НДС и статьёй ОПиУ. Поля шапки
  (организация, контрагент, тип, направление, номер, даты, комментарий) можно
  заполнить только в первой строке документа, как часто выгружает 1С; если в
  двух строках одного документа они разные — документ не загружается, в
  протоколе указаны строки и поле («поле «дата» различается в строках 6 и 7»).
- **Аналитика строк** — новые необязательные колонки: содержание /
  номенклатура, подразделение, ЦФО, проект, продукт/услуга. Ищутся в
  справочниках по названию (ЦФО, проект, продукт — и по коду; проект — в
  организации документа); незнакомое значение — ошибка документа, а не
  тихо пустая аналитика. Мастер сопоставления узнаёт эти колонки по
  заголовкам сам.
- **Ошибка — на весь документ**: документ не загружается без части строк,
  остальные документы файла загружаются. Повторная загрузка по-прежнему
  идемпотентна и заменяет все строки документа — позиции, удалённые из
  документа в 1С, исчезают и здесь. Создание документа и его связи с 1С —
  одна транзакция (раньше два отдельных шага).
- Протокол считает документы и строки начисления: «документов создано 1,
  обновлено 2 (строк начисления: 5), ошибок 2». Шаблон файла содержит
  пример документа из двух строк и необязательные колонки. Файлы «одна
  строка — один документ» загружаются как раньше.
- Чистая логика группировки — `src/lib/integrations/onec-grouping.ts`,
  5 юнит-тестов.

Проверено через интерфейс: шаблон загружен как есть — 2 документа, 3 строки,
все 13 колонок сопоставлены автоматически. Затем файл CSV со своими
заголовками: документ из шаблона пришёл уже с тремя строками (проект найден
по коду «PA», услуга — по названию) и обновился, второй — обновился, новый УПД
создан, документ с разной датой в двух строках и документ с неизвестным
проектом отклонены с понятными сообщениями — «создано 1, обновлено 2 (строк
начисления: 5), ошибок 2». В базе у документа ровно три строки с нужной
аналитикой, контрагент по ИНН создан один раз. Тестовые данные удалены.

- **Не реализовано** (как и раньше): XML/JSON-выгрузки 1С — нужен реальный
  образец выгрузки конкретной конфигурации.

## Дополнение после Этапа 7: Битрикс24 — финансовый результат проекта

Раздел 11 ТЗ хочет видеть в Битрикс24 финансовый результат по сделке или
проекту, а в очередь уходили только статусы оплаты документов. Теперь:

- **Результат проекта** за всё время по проведённым документам — только то,

  выручка, прочие доходы, прямые расходы, прочие отнесённые расходы,
  валовая прибыль, результат, маржа. Общие косвенные расходы компании не

  Денежная часть: получено от клиентов и осталось получить, оплачено
  поставщикам и осталось оплатить — оплата документа делится между
  проектами пропорционально их доле в его сумме.

  этого документа, привязанных к сделке. Ключ идемпотентности — хэш цифр:

  результаты» (например, после привязки сделки). Отправка — тем же вебхуком
  и журналом, что и статусы оплаты.
- **Исправлена ошибка справочников**: при изменении записи очищенное
  необязательное поле не очищалось, а молча сохраняло старое значение (ИНН
  организации, код, ID сделки и т.д.) — побочный эффект исправления создания
  проекта. Теперь при изменении пустое поле записывается как «пусто», если
  колонка это допускает; обязательные в базе колонки (статус проекта)
  сохраняют значение. Новый тест сверяет все справочники со схемой: поле,
  необязательное в форме, должно допускать пустое значение в базе или иметь
  значение по умолчанию — иначе при сохранении была бы ошибка 500.
- Чистая логика — `src/lib/integrations/project-results.ts` (4 теста) и
  `src/lib/dictionaries/columns.ts` (5 тестов). Миграция
  `project_bitrix_deal`.

## Дополнение после Этапа 7: финансовые сценарии — деньги с отсрочками и кредиты

Раньше остаток денег в прогнозе был «предыдущий + операционная прибыль −
платежи по кредитам»: вся выручка считалась полученной в месяц продажи,
поставщики — оплаченными сразу, а кредит был просто оттоком без процентов.
Теперь деньги считаются отдельно от прибыли:

- **Отсрочки оплаты** — два новых драйвера сценария по месяцам, в днях:
  «Отсрочка оплаты клиентов» и «Отсрочка оплаты поставщикам (переменные
  расходы)». Отсрочка в месяцах = дни / 30, дробная часть делит сумму между
  соседними месяцами: при 45 днях половина выручки приходит через месяц,
  половина — через два. Переменные расходы и комиссия посредников
  оплачиваются с отсрочкой поставщикам; постоянные расходы и ФОТ — в том же
  месяце. На прибыль отсрочки не влияют.
- **Старт прогноза** — фактический остаток денег (как и раньше) плюс
  фактическая дебиторка и кредиторка с зарплатой к выплате на сегодня (из
  управленческого баланса, с тем же ограничением видимости): считается, что
  они погасятся в первом месяце. Это меняет цифры существующих сценариев, если
  в системе есть непогашенные документы; в прогнозе это отдельные строки.
- **Кредиты — списком** в сценарии: сумма, месяц получения, ставка % годовых,
  срок, способ погашения (аннуитет, равными долями основного долга, проценты
  ежемесячно и долг в конце срока). Деньги приходят в месяц получения, платежи
  — со следующего; проценты (остаток × ставка / 12) — расход, уменьшают
  «Прибыль после процентов»; погашение основного долга — только отток денег.
  Копейки округляются, последний платёж закрывает долг ровно в ноль.
  Прежний драйвер остался как «Прочие платежи по кредитам/лизингу (вручную,
  без графика)».
- **Прогноз** показывает поступления от клиентов, оплаты поставщикам,
  погашение текущей дебиторки и кредиторки, получение и погашение кредитов,
  проценты, прибыль после процентов, дебиторку, кредиторку и долг на конец
  месяца; карточки — прибыль после процентов и долг на конец горизонта. То же
  — в выгрузке Excel и сравнении сценариев. Без отсрочек и кредитов прогноз
  считается как раньше (проверено прежними тестами).
- Чистая логика — `src/lib/financial-model/cash-timing.ts` (сдвиг по
  отсрочке, график кредита), `project.ts`, `loans.ts`; 16 новых
  юнит-тестов (в т.ч. аннуитет 1 200 000 под 12% на 12 месяцев — 106 618,55 в
  месяц). Таблица `FinancialScenarioLoan` (миграция `scenario_loans`).

Проверено через интерфейс: сценарий с октября 2026 — выручка 200 000 в месяц,

## Дополнение после Этапа 7: исправление и удаление операций банка и кассы

Раньше у операции можно было поменять только классификацию, а ошибочную
операцию — ни исправить, ни удалить; у перевода между собственными счетами
вторая нога при этом никак не менялась. Теперь на странице операции
(«Банк и касса → операция») есть два сворачиваемых блока.

**«Исправить дату, сумму, направление или счёт»** — для операций, введённых
вручную:
- можно поменять дату, направление, сумму, назначение и перенести операцию
  на другой банковский счёт или в кассу (ровно один из двух);
- у перевода между собственными счетами вторая нога меняется вместе с
  первой: та же дата, сумма и назначение, направление — противоположное, её
  счёт остаётся прежним; выбрать счёт второй ноги нельзя (перевод «сам себе»);
- если операция сопоставлена с начислениями, сумму нельзя сделать меньше
  сопоставленной, а направление — поменять (сначала отменить сопоставления);
  статус «сопоставлено / частично» пересчитывается после исправления;
- старый и новый месяц должны быть открыты — из закрытого периода операцию
  не увести и в закрытый не перенести;
- отпечаток защиты от повторного ввода пересчитывается; если исправление
  совпало бы с уже существующей операцией, оно не сохраняется;
- операции из выписки банка не исправляются: дата, сумма и счёт должны
  совпадать с банком. Если выписку загрузили не на тот счёт — операцию
  удаляют и загружают выписку заново.

**«Удалить операцию»** (у перевода — «Удалить перевод (обе операции)»):
- нужно отметить «Да, удалить»; удаление нельзя отменить, операция со всеми
  полями остаётся в журнале аудита;
- операцию с действующими сопоставлениями удалить нельзя — кнопка
  неактивна, пока сопоставления не отменены (иначе у документов незаметно
  пропала бы оплата); отменённые сопоставления удаляются вместе с ней;
- перевод удаляется целиком — обе ноги в одной транзакции БД;
- операция должна быть в открытом периоде;
- удалённая операция из выписки при повторной загрузке той же выписки
  добавится снова — так исправляется ошибочная загрузка.

Заодно:
- сохранение классификации у одной ноги перевода сохраняет её и у второй
  (как при создании перевода), а флажок «Перевод между собственными
  счетами» у связанной пары больше не снимается по одной ноге;
- классификацию операции в закрытом периоде теперь изменить нельзя — раньше
  это проходило, хотя меняло закрытый ДДС;
- исправление, удаление и классификация работают только с операциями в
  зоне видимости пользователя по организациям/подразделениям/проектам;
- все флажки в интерфейсе (подтверждения, права ролей, «в архиве»)
  растягивались на всю ширину строки из-за общего стиля полей ввода —
  исправлено в `globals.css`.

Код: `src/lib/cash/transaction-edit.ts` (разбор формы, проверки
исправления и удаления, 7 тестов), действия `updateBankTransactionAction`
и `deleteBankTransactionAction` в `src/app/(app)/cash/actions.ts`.

Проверено в браузере на временных данных (затем удалены): ручная операция
исправлена (дата, сумма, направление, перенос со счёта в кассу); оба счёта
сразу и перенос в закрытый месяц — понятные отказы; у перевода исправление
и классификация изменили обе ноги, выбор счёта второй ноги отклонён, пара
удалена целиком; с сопоставлением на 150 ₽ уменьшение суммы, смена
направления и удаление отклонены, сумма ровно 150 ₽ сохранилась, после
отмены сопоставления операция удалена вместе с ним. Журнал аудита записал
каждое действие по обеим ногам.

## Дополнение после Этапа 7: заявка на оплату — комментарии согласующих и история по шагам

У каждой заявки появилась своя страница (`/payment-requests/[id]`; в
списке — ссылка на дате срока оплаты и кнопка «История»):
- реквизиты заявки: организация, контрагент, статья, сумма, срок, автор и
  время создания, комментарий автора, маршрут;
- **история согласования по шагам**: для каждого шага маршрута — роль,
  состояние («Согласовано», «Отклонено», «Ждёт решения», «Впереди», «Не
  понадобилось» — для шагов после отклонения или отмены), кто и когда принял
  решение и его комментарий. Решение по шагу, которого в маршруте уже нет
  (маршрут изменили после решения), остаётся в истории с пометкой. Заявка без
  маршрута показывает одну ступень;
- **решение с комментарием**: поле комментария и кнопки «Согласовать» /
  «Отклонить» — только у того, кто вправе решать на текущем шаге. При
  отклонении комментарий обязателен (автор должен понимать, что исправить),
  длина — до 1000 символов;
- кнопки «Отметить оплаченной» и «Отменить заявку» — как в списке.

В списке «Согласовать» по-прежнему нажимается сразу (без комментария), а
«Отклонить…» ведёт на страницу заявки к форме решения, потому что нужна
причина. Под статусом в списке показан комментарий последнего решения.

Защита от устаревшей страницы и одновременных решений:
- форма решения передаёт номер шага, который видел согласующий; если шаг уже
  сменился или заявка уже не на согласовании, решение не принимается, с
  понятным сообщением;
- переход на следующий шаг и запись решения — в одной транзакции, при
  условии, что заявка всё ещё на этом шаге: двое согласующих, нажавших
  одновременно, не примут два решения по одному шагу;
- «Отметить оплаченной» — только из «Согласована», «Отменить» — только из
  «На согласовании» или «Согласована». Раньше со старой страницы можно было,
  например, отметить оплаченной уже отменённую заявку.

В журнал аудита решение пишется вместе с комментарием и номером шага.

Код: `buildApprovalTimeline` и `parseDecisionComment` в
`src/lib/payment-requests/approval.ts` (6 новых тестов), подписи
статусов — `src/lib/payment-requests/labels.ts`.

Проверено в браузере на временных данных (затем удалены по идентификаторам):
маршрут из двух шагов; шаг 1 согласован из списка, шаг 2 — со страницы с

## Дополнение после Этапа 7: платёжный календарь — сетка месяца и перенос срока оплаты заявок

**Перенос срока оплаты заявки.** На странице заявки появился блок «Срок
оплаты»: новая дата и необязательная причина, ниже — история переносов (с
какой даты на какую, кто, когда, почему). В списке заявок под сроком видна
пометка «перенесён» (с числом переносов). Правила:
- переносить могут согласующие заявки (`payment_requests.approve`) и те,
  кто ведёт банк и кассу (`cash.manage`), а также администратор;
- переносится черновик, заявка на согласовании и согласованная; оплаченная,
  отклонённая и отменённая остаются на своей дате;
- срок нельзя перенести в прошлое; статус и шаг согласования при переносе не
  меняются — срок оплаты это решение казначейства о времени платежа, а не о
  самой заявке;
- перенос записывается при условии, что заявку никто не изменил с момента
  открытия страницы (двое, двигающие одну заявку, не перезапишут друг друга
  молча); каждое изменение — в истории переносов и в журнале аудита.

**Платёжный календарь** стал сеткой месяца (недели с понедельника, переход
по месяцам, кнопка «Сегодня»):
- в каждом дне — поступления и платежи за день, карточки заявок на оплату и
  прогнозный остаток на конец дня (отрицательный — красным); прошедшие дни
  без прогноза; сегодняшний день выделен; выходные и праздники — по
  производственному календарю (`production_calendar_days`) с названием
  праздника;
- **заявки видны все, кроме отменённых** (удаления заявок в системе нет —
  ненужную заявку отменяют): согласованные — зелёные, на согласовании —
  жёлтые с пунктиром, оплаченные и отклонённые — серые и в прогноз не входят
  (оплата уже в банковских операциях, отклонённая не будет оплачена);
- переключатель «В прогнозе: согласованные и на согласовании / только
  согласованные» — несогласованные заявки видны в обоих режимах, во втором
  помечены «не входит в прогноз»;

## Дополнение после Этапа 7: платёжный календарь — оплата частями, сроки документов и прогноз по счетам

**Оплата заявки частями.** На странице заявки в блоке «План оплаты» —
«Разбить оплату на части»: строки «дата — сумма» (редактор сразу показывает,
сколько не распределено; кнопки «+ Часть» и «Поровну»). Правила:
- сумма частей равна сумме заявки до копейки, частей от двух до 24, даты не в
  прошлом; сохраняют график согласующие, казначейство и администратор, пока
  заявка не оплачена, не отклонена и не отменена;
- каждая часть отмечается оплаченной отдельно («Оплачено» — право
  `cash.manage`, только у согласованной заявки); заявка остаётся
  «Согласована», пока не оплачена последняя часть, затем становится
  «Оплачена»; «Отметить оплаченной» у всей заявки закрывает и все
  оставшиеся части;
- неоплаченные части можно изменить (перенос даты части попадает в историю
  переносов с номером части), оплаченные зафиксированы; «Объединить в один
  платёж» — пока ни одна часть не оплачена;
- срок заявки в списке, фильтрах и чек-листе закрытия месяца — ближайшая
  неоплаченная часть; в списке заявок видно «частями: оплачено N из M»;
  на дашборде «согласованные заявки» считаются за вычетом оплаченных частей.

**Сроки документов начислений из календаря.** Непогашенные проведённые
документы теперь в календаре отдельными карточками (к получению — с зелёной
кромкой и «+», к оплате — с тёмной кромкой и «−»; у частично оплаченных —
остаток). Карточку можно перетащить на другой день — меняется срок оплаты
документа. На странице документа — блок «Срок оплаты» с формой переноса
(с причиной) и историей переносов. Правила:
- меняется только срок оплаты — суммы, строки и проводки остаются прежними,
  поэтому это можно у проведённого документа и в закрытом периоде (срок —
  договорённость о платеже, не учётная цифра); отменённый и оплаченный
  документ не переносится; срок не в прошлом;
- право — у тех, кто ведёт начисления (`accruals.manage`) или деньги
  (`cash.manage`), и у администратора;
- перенос записывается при условии, что документ не изменили с момента
  открытия (по версии документа); каждый перенос — в истории документа
  (`AccrualDueDateChange`) и в журнале аудита; отчёт о задолженности
  сразу считает просрочку по новому сроку.

**Прогноз по счетам и организациям.** У заявки (при создании и на её
странице) и у документа (на его странице) можно указать счёт или кассу
оплаты — только своей организации. В календаре:
- фильтры «Организация» и «Счёт или касса»: остаток, прогноз, сетка и сводка
  считаются только по выбранной организации (все её счета и её платежи) или
  по одному счёту (его остаток и платежи, для которых он назначен);
- в срезе по счёту платежи той же организации без счёта оплаты показаны
  отдельной полосой «Счёт оплаты не назначен» — в прогноз счёта они не
  входят; выбрав платёж, можно сразу назначить ему счёт (и перенести дату);
- под сеткой — таблица «Прогноз по счетам»: у каждого счёта остаток сейчас,
  поступления и платежи, назначенные на него, остаток на конец месяца и
  минимум в месяце с датой (красным — если уходит в минус), плюс строка
  платежей без счёта; название счёта — ссылка на его срез.

## Дополнение после Этапа 7: импорт справочников — обновление, защита от дублей, реквизиты контрагентов

Загрузка справочника из Excel больше не только добавляет записи.

**Как строка находит запись:**
- в выгрузке появилась колонка «ID записи»: строка с ID обновляет именно эту
  запись (так можно переименовать запись или поменять любой реквизит);
- строка без ID ищет запись по ключевым полям по порядку — ИНН → код → номер
  счёта → название (у каждого справочника свои, список показан на странице
  импорта): одна найденная — обновляется, ни одной — создаётся новая,
  несколько — ошибка с просьбой указать ID;
- следующий ключ подхватывает только записи, у которых предыдущие ключи
  пусты: контрагент без ИНН найдётся по названию, а контрагент с другим ИНН —
  нет (это другая организация, будет создана новая запись);
- обновляются только изменившиеся поля из колонок, которые есть в файле;
  пустая ячейка очищает необязательное поле (как в форме), колонка
  «Статус записи» («В архиве» / «Активна») отправляет в архив и возвращает.

**Защита от дублей:** повторная загрузка того же файла (или только что
скачанной выгрузки) ничего не меняет — всё «без изменений»; две строки файла
про одну запись или одна и та же новая запись дважды — ошибка с номерами
строк. По-прежнему всё или ничего: при любой ошибке не меняется ни одна
запись, иначе все изменения — одной транзакцией.

**Проверка без сохранения:** кнопка «Проверить без сохранения» показывает,
сколько записей будет создано, обновлено, осталось без изменений, и список
строк с изменяемыми полями («Строка 2: обновится «ООО Альфа» — Полное
наименование, Посредник»). **Режим «Не трогать, только добавлять новые»** —
существующие записи пропускаются. После загрузки список справочника
показывает итог, в журнал аудита пишутся файл, режим, числа и ID
обновлённых записей.

**Реквизиты и контакты контрагентов:** выгрузка контрагентов содержит листы
«Банковские реквизиты» и «Контакты» (с ID, ИНН и наименованием контрагента),
загрузка их читает: контрагент строки — по ID, ИНН или наименованию, в том
числе новый из этого же файла; счёт сопоставляется по номеру и БИК, контакт —
по имени; «да» в колонке «Основной» делает счёт основным, у каждого
затронутого контрагента после загрузки ровно один основной счёт. Строки,
которых нет в файле, не удаляются. Реквизиты и контакты проверяются теми же
правилами, что и в форме.

Заодно: при загрузке теперь проверяются те же правила полей, что и в форме
(например, контрольная цифра ИНН), — раньше загрузка их пропускала. Общий
разборщик файлов умеет отдавать все листы книги (`parseWorkbookSheets`).

## Дополнение после Этапа 7: средний заработок — индексация, стаж, МРОТ, районный коэффициент, замена лет

**История окладов.** При изменении оклада в карточке сотрудника
указывается, с какой даты действует новый оклад; изменение записывается в
историю занятости («Изменение оклада: 100 000 → 120 000»), при приёме —
начальный оклад. Миграция `average_earnings_indexation`.

**Индексация отпускных (п. 16 Положения № 922).** Галочка «оклады повышены
в организации или подразделении — индексировать» (это условие закона, его
подтверждает бухгалтер; если в периоде было повышение оклада, система сама
подсказывает об этом):
- повышение внутри расчётного периода — выплаты месяцев до повышения,
  зависящие от оклада, умножаются на «оклад в конце периода / оклад в
  месяце»; премии фиксированной суммой не индексируются. Что зависит от
  оклада — новая отметка вида начисления «Индексируется при повышении
  оклада» (оклад и аванс отмечены миграцией и в начальных данных);
  месяц, в котором оклад повысили, не индексируется;
- повышение после расчётного периода, до начала отпуска, — индексируется
  весь средний дневной заработок;
- повышение во время отпуска — с коэффициентом оплачиваются дни с даты
  повышения.
Расшифровка показывает коэффициент и заработок после индексации по месяцам.

**Больничные:**
- **страховой стаж по данным системы** — в карточке сотрудника «страховой
  стаж до приёма, месяцев», к нему прибавляются полные месяцы работы у нас;
  процент (60/80/100) и признак «меньше 6 месяцев» определяются
  автоматически; выбрать вручную по-прежнему можно;
- **стаж меньше 6 месяцев** (ч. 6 ст. 7 Закона № 255-ФЗ) — пособие за
  каждый день не больше МРОТ (× районный коэффициент) / дней месяца
  болезни, по каждому месяцу отдельно; расшифровка показывает ограничение;
- **районный коэффициент** — новое поле организации (от 1 до 3); минимум из
  МРОТ и ограничение при коротком стаже считаются с ним;
- **замена лет расчётного периода** по заявлению сотрудника (ч. 1 ст. 14):
  годы замены и справки о заработке у других работодателей за них;
  система считает пособие с заменой и без неё и применяет замену, только
  если пособие больше, — иначе объясняет, почему не применила.

Комментарий строки расчёта и журнал аудита содержат индексацию,
стаж, районный коэффициент, годы расчёта и замену.

правилом, что и форма (например, районный коэффициент).

## Дополнение после Этапа 7: табель — графики, сверхурочные, выходные, командировки

**Графики работы.** Справочник «Графики работы» теперь задаёт сам график:
вид — «пятидневка по производственному календарю» или «сменный: N смен

## Дополнение после Этапа 7: резервные копии — вторая копия в другом месте

Копия на том же диске, что и база, не защищает от потери диска. Теперь
`npm run db:backup` после создания и проверки копии кладёт её вторую копию в
папку `BACKUP_MIRROR_DIR` (в `.env`): другой диск, сетевую папку
(`\\сервер\папка`) или папку облачного диска (OneDrive, Яндекс Диск —
клиент облака сам отправит её в облако).
- Копия пишется во временный файл, сверяется с оригиналом по SHA-256 и
  только потом получает своё имя — недописанная копия не выглядит готовой.
- Своя ротация: `BACKUP_MIRROR_KEEP` (по умолчанию как `BACKUP_KEEP`);
  другие файлы в этой папке не трогаются.
- **Шифрование**: с `BACKUP_MIRROR_PASSWORD` (не короче 12 символов) вторая
  копия шифруется — AES-256-GCM, ключ из пароля через scrypt, файл
  `.dump.enc` — и сразу пробно расшифровывается со сверкой SHA-256: копию,
  которую нельзя восстановить, система не считает сделанной. Так финансовую
  базу можно держать в облаке, не открывая её облачному сервису.
  Расшифровать для восстановления — `npm run db:backup:decrypt -- файл.dump.enc`
  (пароль — из той же переменной); неверный пароль или повреждённый файл —
  понятная ошибка, недорасшифрованный файл не остаётся. Пароль нужно хранить
  отдельно от сервера — без него зашифрованную копию не восстановить.
- Если вторая копия не удалась (папка недоступна, совпадает с основной,
  короткий пароль), основная копия остаётся, но скрипт завершается с кодом
  2 — Планировщик покажет ошибку задачи; в журнале запусков (`backup_runs`,
  поля `mirrorStatus` / `mirrorDetails`, миграция `backup_mirror`) и в
  `backups/backup.log` — причина.
- Если вторая копия на том же диске, что и основная (например, папка
  OneDrive на диске C:), в подробностях — предупреждение: от потери диска
  это защищает, только пока облако её синхронизирует.
- Страница «Резервные копии»: колонка «Вторая копия», под статусом —
  результат последней второй копии (или предупреждение, что она не
  настроена / не удалась). `/api/health`: `backup.mirror` — `ok` /
  `failed` / `off`.
- Настройки описаны в `.env.example`; задача Планировщика читает `.env`,
  поэтому достаточно добавить туда строки.

Код: `scripts/backup-crypto.mjs` (шифрование и сверка), `resolveMirrorDir` /
`mirrorWarning` в `scripts/backup-core.mjs`, `scripts/backup-decrypt.mjs`;
7 тестов (`scripts/backup-mirror.test.ts`, `status.test.ts`): папка и
предупреждение, ротация зашифрованных копий, шифрование и расшифровка
файла 300 КБ, неверный пароль, повреждённый файл, не зашифрованный файл,
короткий пароль.

Проверено на этой машине: копия базы (179 КБ, 66 таблиц) со второй
зашифрованной копией во временную папку — «MIRROR OK», предупреждение «на
том же диске C:»; `db:backup:decrypt` восстановил файл, совпадающий с
основной копией по SHA-256, `pg_restore --list` показал 66 таблиц; неверный
пароль — отказ без остатка файла; вторая папка, совпадающая с основной, —
основная копия сделана, «MIRROR FAILED», код выхода 2, предупреждение на
странице и `"mirror":"failed"` в `/api/health` (записи этих проверочных
запусков затем удалены). На этом компьютере только диск C:, поэтому для
настоящей защиты подойдёт сетевая папка или папка OneDrive (она есть в
`C:\Users\User\OneDrive`) с паролем шифрования — это настройка
`.env`, которую нужно выбрать самим.

## Дополнение после Этапа 7: управленческий баланс — баланс на прошлую дату, амортизация и проценты по займам

**Баланс на прошлую дату.** Сопоставление платежа с документом начисления
действует с более поздней из двух дат — платежа и документа. Баланс на
прошлую дату видит тогдашние долги и авансы, даже если платёж сопоставили
позже: предоплата до даты документа остаётся авансом, документ до даты
платежа не оплачен. Дата, когда сопоставление ввели в систему, роли не
играет; отменённые сопоставления не учитываются. Дебиторка и кредиторка
считаются по всем проведённым документам на дату, а не только по
неоплаченным сегодня.

**Основные средства и амортизация.** Новый справочник «Основные средства»:
- наименование, инвентарный номер, организация, подразделение
  (необязательно);
- первоначальная стоимость, дата ввода в эксплуатацию, срок полезного
  использования в месяцах (1–600);
- расходная статья ОПиУ для амортизации, дата выбытия.

Амортизация линейная: стоимость / срок, с месяца после ввода. Последний
месяц добирает копейки округления, чтобы за срок списалась ровно
стоимость. После месяца выбытия амортизация не начисляется. Сама стоимость
в баланс приходит как раньше — через статью ДДС покупки, привязанную к
статье баланса «Основные средства», или балансовой операцией. Реестр только
начисляет амортизацию.

**Займы и кредиты.** Новый справочник «Займы и кредиты»:
- название, организация, ставка % годовых;
- дата начала начисления, дата окончания договора (необязательно);
- расходная статья ОПиУ для процентов;
- своя статья баланса займа — обязательство без системного кода.

Остаток долга — это операции по статьям ДДС, привязанным к статье займа
(получение, погашение; переводы не учитываются), плюс балансовые операции
по ней. Проценты начисляются каждый день: остаток на начало дня × ставка /
365 (в високосный год 366). День получения денег не начисляется, день
погашения начисляется. Сумма за месяц округляется до копеек.

**Как начисления попадают в отчёты.** Начисление месяца относится к его
последнему дню, поэтому ОПиУ за месяц и баланс на конец месяца согласованы.
Баланс на середину месяца текущий месяц ещё не включает.
- **ОПиУ.** Суммы добавляются в строки своих статей с пометкой «в т.ч.
  амортизация и проценты без документов». Сравнение с бюджетом по статье
  остаётся верным. В выгрузке Excel — отдельная строка под статьёй.
- **Фильтры ОПиУ.** Фильтр по организации и ограничение доступа по
  организациям учитываются. По подразделению в отчёт попадают основные
  средства этого подразделения, займы не попадают. При фильтре по ЦФО,
  проекту, продукту или контрагенту начислений в отчёте нет — у них нет
  этих разрезов.
- **Баланс.** Системные строки «Накопленная амортизация» (актив, со знаком
  минус) и «Проценты к уплате» (обязательство) показывают начисленное по
  реестру плюс операции по ним. Остаток накопленной амортизации на начало
  учёта вводится балансовой операцией со знаком «−». Уплату процентов
  проводите по статье ДДС, привязанной к «Проценты к уплате».
  Нераспределённая прибыль включает амортизацию и проценты, так что
  контрольное равенство сохраняется. Миграция
  `fixed_assets_and_credit_agreements` добавляет эти строки и статью
  «Основные средства» в существующую базу.
- **Архив.** Архивные записи реестров тоже считаются — это история.
- **Закрытые периоды.** Правка, которая задним числом поменяла бы
  амортизацию или проценты закрытого периода (стоимость, срок, даты,
  ставка, статьи, организация), не сохраняется — ни из формы, ни из
  загрузки Excel. Переименовать запись можно.

Для этого у справочников появилась проверка записи целиком
(`validateRecord` в `DictionaryConfig`). Её вызывают создание, изменение

## Дополнение после Этапа 7: финансовые сценарии — сроки текущих долгов, отсрочка по услугам, льготный период и налог

**Текущие дебиторка и кредиторка — по срокам оплаты.** Прогноз берёт
остаток каждого проведённого документа начисления на сегодня (с тем же
ограничением видимости, что и управленческий баланс) и его срок оплаты.
Если срок не указан, берётся дата документа.
- Просроченное и то, что со сроком в первом месяце прогноза, гасится в
  первом месяце.
- Остальное — в месяц своего срока.
- Срок после горизонта — долг остаётся в дебиторке или кредиторке на конец
  прогноза.

Над прогнозом написано, сколько долгов гасится позже первого месяца.

**Своя отсрочка оплаты клиентов у новой услуги.** В форме новой услуги
(добавление и правка) есть поле «Отсрочка оплаты клиентов, дней». Если оно
заполнено, выручка услуги поступает с этой отсрочкой. Пусто — как у
сценария (драйвер «Отсрочка оплаты клиентов»). Отдельных клиентов в
сценарии нет, поэтому отсрочка задаётся по услуге.

**Кредиты — льготный период и досрочное погашение.** У кредита в сценарии
появились поля «Льготный период, мес.» и «Досрочное погашение: месяц /
сумма».
- В льготный период платятся только проценты, а долг гасится выбранным
  способом за оставшиеся месяцы срока.
- Досрочное погашение — разовая сумма сверх планового платежа. Срок
  сохраняется, платёж дальше пересчитывается на новый остаток. Если сумма
  больше долга, кредит закрывается.
- Проверки формы: льготный период меньше срока; месяц досрочного
  погашения — один из месяцев платежей; месяц и сумма заполняются вместе.

**Налог в прогнозе.** Блок «Налог» на странице сценария задаёт режим и
ставку. Если ставка не указана, берётся стандартная.

| Режим | Ставка по умолчанию | База |
|---|---|---|
| Не считать | — | — |
| УСН «доходы» | 6 % | деньги от клиентов, включая погашение текущей дебиторки |
| УСН «доходы минус расходы» | 15 % | полученное минус оплаченные расходы (поставщики, текущая кредиторка, постоянные, ФОТ, проценты); за год не меньше 1 % доходов (минимальный налог) |
| Налог на прибыль | 25 % | прибыль после процентов по методу начисления |

- **Начисление.** Налог считается нарастающим итогом с начала
  календарного года в пределах прогноза; начисление месяца — прирост за
  месяц. Убыток уменьшает налог года.
- **Уплата.** Авансовый платёж за квартал — в апреле, июле и октябре, за
  год — в марте следующего года. Переплата не возвращается, а уменьшает
  следующие платежи года.
- **Прогноз.** Добавлены строки «Прибыль до налога», «<режим> —
  начислено», «Чистая прибыль», «Уплата налога» и «Налог к уплате на конец
  месяца». Карточка сверху показывает чистую прибыль после налога. То же в
  выгрузке Excel; в сравнении сценариев — чистая прибыль и налог за 12
  месяцев.
- **Не считаются:** НДС, налоги за месяцы до начала прогноза, уменьшение
  УСН «доходы» на страховые взносы. Если нужна другая ставка, задайте её
  вручную.

Без налога, сроков и льготных условий прогноз считается как раньше (прежние
37 тестов модели не менялись). Миграция `scenario_taxes_terms_grace`.

## Дополнение после Этапа 7: система налогообложения и ставки налогов в карточке организации

**Система налогообложения.** В справочнике «Организации и ИП» появилось
поле «Система налогообложения»: ОСН, УСН «доходы», УСН «доходы минус
расходы», АУСН «доходы», АУСН «доходы минус расходы», ЕСХН, патент. Оно
показано и в списке организаций. Существующие организации получили ОСН —
при другой системе поменяйте её в карточке.

**Налоги и ставки.** Под формой карточки организации — блок «Налоги и
ставки». Налоги:
- налог на прибыль;
- НДС;
- налог по УСН, по АУСН, ЕСХН;
- налог на имущество;
- страховые взносы — единый тариф;
- взносы на травматизм.

Как работают ставки:
- У каждой ставки есть дата начала. Ставка действует до дня перед
  следующей ставкой того же налога, поэтому история сохраняется.
- Чтобы поменять ставку с нового года, добавьте запись с новой датой.
  Прежние периоды считаются по старой ставке.
- В таблице видно, с какой даты и по какую действует ставка, а над ней —
  какие ставки действуют сейчас.
- Строку можно изменить на месте или удалить.
- Две ставки одного налога с одной даты не сохраняются: ставка от 0 до
  100 %, дата обязательна.
- Кнопка «Заполнить стандартными» добавляет стандартные ставки выбранной
  системы с указанной даты, только по налогам без ставок: ОСН — налог на
  прибыль 25 % и НДС 22 %; УСН — 6 % или 15 %; АУСН — 8 % или 20 %; ЕСХН — 6 %.
- Все изменения пишутся в журнал аудита.

**Где используются ставки:**
- **Зарплата.** «Страховые взносы — единый тариф» заменяют пенсионные,
  медицинские и социальные взносы из справочника «Налоговые и страховые
  правила», а «Взносы на травматизм» — общий тариф на травматизм. Ставка
  берётся на дату выплаты расчёта и только для этой организации (например,
  пониженный тариф МСП или свой класс риска). НДФЛ по-прежнему общий.
- **Финансовые сценарии.** В блоке «Налог» есть режим «Как у организации».
  Система налогообложения и ставки берутся из карточки выбранной
  организации; ставка каждого года — действующая на 1 января, а без своей
  ставки — стандартная. Поменяли систему или ставку в карточке — прогноз
  пересчитается сам.
- **Новые режимы прогноза.** Добавлены АУСН (уплата каждый месяц за
  предыдущий, минимальный налог 3 % доходов в режиме «доходы минус
  расходы») и ЕСХН (уплата за полугодие в июле и за год в марте). Патент в
  прогнозе не считается: его стоимость задайте постоянными расходами.
- **Пока не используются:** НДС и налог на имущество хранятся в карточке,
  но в прогнозе не считаются.

## Дополнение после Этапа 7: страховые взносы ИП за себя

В блоке «Налоги и ставки» карточки ИП появились два налога. Юрлицам они не
показываются, а сервер их не принимает.

- **Фиксированные взносы за себя** — сумма за год в рублях, ставки у них
  нет. Срок уплаты — 28 декабря.
- **Взносы с дохода свыше порога** — ставка (обычно 1 %), порог дохода за
  год (обычно 300 000 ₽) и, по желанию, максимум взносов за год. Срок
  уплаты — 1 июля следующего года.

Как и остальные ставки, взносы действуют с даты до следующей записи того же
вида. На новый год добавьте запись с новой суммой и максимумом.

**Стандартные ставки.** Кнопка «Заполнить стандартными» у ИП (кроме АУСН,
где взносов за себя нет) добавляет оба вида с суммами года, с которого
действуют ставки. Суммы взяты из ст. 430 НК РФ — перед использованием
сверьте их с действующей редакцией:

| Год | Фиксированные | Максимум взносов 1 % |
|---|---|---|
| 2024 | 49 500 ₽ | 277 571 ₽ |
| 2025 | 53 658 ₽ | 300 888 ₽ |
| 2026 | 57 390 ₽ | 321 818 ₽ |
| 2027 | 61 154 ₽ | 343 340 ₽ |

Для других лет фиксированные взносы не предлагаются, а максимум остаётся
пустым — введите их сами.

Для экрана ставки подписываются так: «57 390,00 ₽ в год» и «1% с дохода
свыше 300 000,00 ₽, не более 321 818,00 ₽ в год».

**В финансовых сценариях.** При налоге «как у организации» для ИП прогноз
считает и взносы за себя:
- **Фиксированные** — сумма года равными долями по месяцам, в сумме ровно
  годовая; уплата в декабре.
- **С дохода** — ставка × (доход с начала года − порог), нарастающим
  итогом, не больше максимума; уплата в июле следующего года.
- **Доход для взносов:** при УСН «доходы» — полученные деньги; при УСН
  «доходы минус расходы», ОСН и ЕСХН — полученное минус оплаченные расходы.
- **Патент:** только фиксированные взносы — потенциальный доход прогноз не
  знает. **АУСН:** взносов нет.
- **Строки прогноза:** «Взносы ИП за себя — начислено», «Уплата взносов ИП
  за себя», «Взносы ИП к уплате на конец месяца». Взносы уменьшают чистую
  прибыль и деньги. То же в выгрузке Excel; в сравнении сценариев — вместе с
  налогом.

## Дополнение после Этапа 7: уменьшение налога УСН на страховые взносы

В прогнозе с налогом «как у организации» при УСН «доходы» налог уменьшается
на страховые взносы нарастающим итогом с начала года. Лимит зависит от того,
есть ли сотрудники:

- **ИП без сотрудников** — налог уменьшается на взносы за себя
  (фиксированные и 1 % с дохода) полностью.
- **Есть сотрудники** — налог уменьшается на взносы за себя и взносы за
  сотрудников, но не больше чем на 50 % налога с начала года.
- **У организации** (не ИП) — на взносы за сотрудников, не больше 50 %.

Взносы за сотрудников — их доля в ФОТ сценария: стоимость сотрудника
включает взносы. Ставка — единый тариф и травматизм из карточки
организации или общие правила на 1 января первого года прогноза.

**Когда считается, что сотрудники есть** — лимит переключается сам, без
отдельной настройки:
- в справочнике «Сотрудники» есть работающий сотрудник этой организации —
  лимит 50 % на весь прогноз;
- или в сценарии численность в месяце больше нуля (прочий персонал,
  подразделения или персонал новых услуг) — лимит 50 % с этого месяца до
  конца года.

Если взносы больше налога, начисление месяца бывает отрицательным: налог с
начала года уменьшился. Переплату прогноз не возвращает, она уменьшает
следующие платежи года.

**Взносы как расход.** При других режимах взносы ИП за себя — расход:
- при УСН «доходы минус расходы» и ЕСХН — уплаченные (кассовый метод);
- при ОСН — начисленные.

**Где видно:**
- в прогнозе — строка «в т.ч. уменьшение налога на страховые взносы», то
  же в выгрузке Excel;
- в подписи налога сценария — какой лимит действует («полностью, пока нет
  сотрудников» или «не больше чем на 50% — есть сотрудники (N)»);
- в карточке организации на УСН «доходы» — сколько работающих сотрудников и
  какое правило действует сейчас.

## Дополнение после Этапа 7: НДС до прогноза, вычет по постоянным расходам, освобождение на УСН, даты деятельности

**НДС до начала прогноза.** Берётся из проведённых документов начисления
(«в т.ч. НДС» в строках): по доходным — начисленный, по расходным — к
вычету (при ставках с вычетом).
- **Прошлый квартал:** его трети уплачиваются в месяцах квартала начала
  прогноза. Трети до начала прогноза считаются уплаченными, остальные
  входят в «НДС к уплате» и платятся по сроку.
- **Месяцы текущего квартала до прогноза:** входят в НДС этого квартала.

**Входящий НДС по постоянным расходам.** Новый драйвер сценария
«Постоянные расходы с входящим НДС (доля, для вычета НДС)», по умолчанию

## Дополнение после Этапа 7: доходы и расходы без НДС, строка «НДС к уплате»

В документах начисления сумма строки хранится с НДС: колонки «Сумма» и «в
т.ч. НДС», так же при загрузке из 1С. Раньше эта сумма целиком попадала в
выручку и расходы. Теперь в ОПиУ, маржинальность, нераспределённую прибыль
баланса и финансовый результат проекта для Битрикс24 идёт сумма без НДС:

- **Выручка** — всегда за вычетом НДС: НДС, полученный от клиента, не
  доход, а налог к уплате.
- **Расходы** — за вычетом входящего НДС, только если организация
  принимает его к вычету на дату документа:
  - на ОСН — да;
  - на УСН и ЕСХН — если в карточке организации на эту дату есть ставка
    НДС с вычетами (22 % или 10 %);
  - при ставках 5 % и 7 %, без ставки, на АУСН и патенте — нет, НДС
    остаётся в расходе.
- **Долги и деньги остаются с НДС:** дебиторка, кредиторка, оплаты,
  сопоставления — клиент и поставщик платят всю сумму. В результате
  проекта полученное и остаток к получению тоже с НДС.

**Строка баланса «НДС к уплате»** — обязательство, системная строка:
- считается как НДС из доходных документов минус входящий НДС к вычету,
  плюс балансовые операции по строке;
- уплату НДС в бюджет проводите по статье ДДС, привязанной к этой строке, —
  она уменьшает долг;
- без неё баланс разошёлся бы на НДС: дебиторка — с НДС, прибыль — без.

Миграция `vat_payable_balance_line` добавляет строку в существующую базу,
`prisma/seed.ts` — в новую.

где в документах указан НДС, теперь показывают суммы без НДС. Снимки уже
закрытых периодов (контрольные остатки при закрытии) не пересчитываются.
Плановые суммы бюджета сравниваются с фактом без НДС — если план вводили с
НДС, его стоит поправить.

на прибыль, теперь тоже без НДС.

## Дополнение после Этапа 7: окончательный расчёт зарплаты — расход месяца, за который начислен

Раньше проводка расчёта зарплаты в ОПиУ шла датой выплаты. Окончательный
расчёт за сентябрь выплачивается 10 октября, поэтому зарплата сентября
делилась: аванс — в сентябре, остаток — в октябре. По методу начисления вся
она — расход сентября.

- **Дата расхода.** Окончательный расчёт теперь проводится последним днём
  месяца, за который начислен: выплата 10.10.2026 — документ от 30.09.2026.
  Аванс и разовые выплаты — как раньше, датой выплаты. Отпуск в
  окончательном расчёте делится по дням относительно этого месяца. Функция
  `accrualDateForRun` в `src/lib/payroll/post-to-accrual.ts`.
- **Документ и период.** Номер документа — по месяцу расхода («ФОТ-2026-09-…»),
  документ привязан к учётному периоду этого месяца. В комментарии указана
  дата выплаты.
- **Баланс.** На конец месяца начисленная, но ещё не выплаченная зарплата —
  в строке «Налоги и зарплата к выплате».
- **Закрытый месяц.** Если месяц, за который начислен расчёт, уже закрыт,
  утверждение не проходит. Сообщение объясняет: откройте период, утвердите
  расчёт и закройте период снова. Иначе расход задним числом изменил бы
  закрытый месяц.
- **Контрольный лист закрытия месяца.**
  - Окончательный расчёт за этот месяц с выплатой в следующем должен быть
    утверждён; он считается в месяце, за который начислен, а не в месяце
    выплаты.
  - Новое предупреждение: у организации есть аванс за месяц, а
    окончательного расчёта ещё нет.

Уже проведённые расчёты не перепроводятся — правило действует для новых
утверждений; в базе на момент изменения расчётов не было.

## Дополнение после Этапа 7: суммированный учёт рабочего времени

У графика работы появилось поле «Суммированный учёт: учётный период, мес.»:
1, 3, 6 или 12 месяцев, пусто — обычный учёт по дням (ст. 104 ТК РФ).
Другие значения форма не принимает. Учётные периоды выровнены по
календарному году: квартал, полугодие, год. Миграция
`summarized_working_time`.

**Как считается переработка** — в окончательном расчёте за последний месяц
учётного периода, отдельной строкой «Сверхурочные» с расшифровкой:
- **Норма** — по производственному календарю при 40-часовой неделе (с
  сокращёнными предпраздничными днями) за время работы у нас, минус часы,
  приходящиеся по календарю на дни отпуска, болезни, командировок и
  отсутствия (Приказ № 588н).
- **Отработано** — часы табеля (работа, сверхурочные, проекты) в рабочие
  по графику дни; без отметок — часы смены по графику.
- **Что сюда не входит:** работа в выходные по графику и смены в
  праздники (ст. 112) — они оплачиваются по ст. 153 строкой «Работа в
  выходные и праздники» и сверхурочной не считаются (ст. 152).
- **Переработка** = отработано − норма. Оплата: первые 2 часа за весь
  учётный период × 1,5, остальные × 2.
- **Часовая ставка** — оклад / средняя месячная норма часов учётного
  периода по календарю.
- **Отметки «Сверхурочные» по дням** у сотрудников с суммированным учётом
  отдельно не оплачиваются: их часы входят в отработанные, иначе переработка
  оплачивалась бы дважды.

Код: `summarizedPeriod` и `computeSummarizedOvertime` в
`src/lib/payroll/work-calendar.ts`, расчёт — `src/lib/payroll/calculate.ts`.

Тесты: 4 новых (всего 392):

- отпуск 1–14 июля уменьшает норму на 80 ч и отработанное на 96 ч —
  переработка 8 ч, 15 000 ₽;

## Дополнение после Этапа 7: автоматическая загрузка выписок по API банков

Раздел «Интеграции → Банки: выписка по API» (`/integrations/banks`): счёт из
справочника «Банковские счета» подключается к API банка, и его операции
загружаются в «Банк и касса» сами, без файлов выписки — как в сервисах
вроде Финолога.

**Банки.**
- **Т-Банк (Тинькофф Бизнес)** — токен Open API из интернет-банка. Выписка:
  `GET /api/v1/statement` с постраничной выдачей.
- **Точка** — JWT-токен из интернет-банка. Выписка заказывается
  (`POST /statements`) и забирается, когда готова; у счёта должен быть
  заполнен БИК.
- **Сбер (СберБизнес API)** и **Альфа-Банк (Alfa API)** — приложение,
  зарегистрированное в кабинете разработчика банка: client_id,
  client_secret, refresh_token и клиентский сертификат .pfx (путь к файлу на
  этом компьютере и пароль).
  - Токен доступа обновляется по refresh_token, новые токены сохраняются.
  - Выписка запрашивается по дням (`statement/transactions`).
  - Выписка текущего дня, если банк её ещё не сформировал, берётся при
    следующей загрузке.

**Как загружается.**
- **Один путь с файлом выписки.** Загрузка файла и загрузка по API идут
  через общий модуль `importStatementOperations`
  (`src/lib/bank-import/import-operations.ts`): защита от дублей,
  контрагент по ИНН (ИНН теперь сохраняется и у операции), статья и
  разрезы по правилам классификации, запись загрузки в истории импорта.
- **Дубли.** Операции из API опознаются по счёту, дню, направлению, сумме
  и назначению — так же, как строки файла без номера операции. Поэтому
  выписка, загруженная раньше файлом, по API не задваивается, и наоборот.
  Одинаковые операции за день (например, две одинаковые комиссии) не
  склеиваются.
- **Период загрузки.** Первая загрузка — с указанной даты. Дальше — с дня
  последней успешной загрузки минус 3 дня: банки проводят операции и
  задним числом, а дубли отсекаются. Дни считаются по Москве, день операции
  берётся из даты банка без сдвига часовых поясов.
- **Итог загрузки** пишется в строку подключения: период, сколько операций в
  выписке, сколько новых, сколько уже было, сколько пропущено неполных.
  Ошибки банка объясняются, например: «банк отклонил доступ (401) —
  проверьте токен». Второй одновременный запуск по тому же счёту
  пропускается.

**Реквизиты.**
- Шифруются тем же способом, что ключ DaData: `src/lib/crypto/secret-box`,
  AES-256-GCM, ключ из `AUTH_SECRET`.
- На экран выводятся только последние 4 символа, в журнал аудита не
  попадают.
- Перед сохранением система запрашивает выписку за сегодня — неверные
  реквизиты не сохраняются.
- Удаление подключения стирает реквизиты, загруженные операции остаются.
- Если сменить `AUTH_SECRET`, реквизиты придётся ввести заново — страница
  об этом скажет.

**По расписанию** — задача Планировщика Windows, как у резервных копий:
- `powershell -ExecutionPolicy Bypass -File scripts\register-bank-sync-task.ps1`
  — каждые 30 минут; `-Minutes 60` — раз в час; `-Remove` — удалить.
- Задача запускает `npm run bank:sync` (`scripts/bank-sync.ts`) — все
  включённые подключения по очереди — и пишет журнал в
  `backups\bank-sync.log`. Код выхода 2 означает ошибку хотя бы по одному
  счёту.
- На странице: «Загрузить сейчас» (по счёту), «Загрузить все счета сейчас»,
  «Выключить» / «Включить», «Заменить реквизиты», «Удалить».

Миграция `bank_api_connections` (таблица `bank_connections`). Права:
управление подключениями — «Управление интеграциями», ручной запуск
загрузки — «Управление движением денег».

Код:
- `src/lib/bank-api/core.ts` — реквизиты, HTTP с клиентским

- `providers.ts` — банки;

## Дополнение после Этапа 7: массовое удаление операций и история загрузок выписок

**Удаление отмеченных операций.** В списке «Банк и касса» у каждой строки
флажок, в заголовке — «Отметить все», над таблицей — «Удалить отмеченные» с
подтверждением «Да, удалить». Правила те же, что у удаления одной операции:
- перевод между своими счетами удаляется целиком, даже если отмечена одна
  его нога;
- операции с действующими сопоставлениями и в закрытых периодах
  пропускаются, в сообщении — какие и почему;
- удаляются только операции в зоне видимости пользователя, не больше 500

## Дополнение после Этапа 7: платёжный календарь — время платежа и остаток в течение дня

**Время платежа.** У срока оплаты появилось необязательное время «ЧЧ:ММ»,
например отсечка банка или час, когда заказчик обещал оплату. Пусто — «в
течение дня», как раньше.
- **Где задаётся:**
  - в новой заявке и в форме доработки;
  - при переносе срока на странице заявки и документа начисления;
  - у каждой части графика оплаты;
  - в календаре: выбрать платёж → дата и время → «Перенести».
- **Перетаскивание** меняет только день, время остаётся прежним.
- **История переносов** показывает и время: «14.10.2026 в 10:00 →
  14.10.2026 в 13:45».
- **Где видно:** время показано в карточке заявки, в списке заявок
  («в 10:00»), в уведомлениях и на карточках календаря. В дне календаря
  платежи идут по времени.

**Остаток в течение дня.** Раньше остаток считался только на конец дня.
Утренний платёж и дневное поступление взаимно гасились — кассовый разрыв
до обеда был не виден. Теперь движения дня проходят по порядку:
- платёж без времени — в начале дня;
- поступление без времени — в конце дня;
- при одинаковом времени — сначала платежи.

Это осторожная оценка: без времени считаем худший вариант. Просроченный
платёж считается в начале сегодняшнего дня, прежнее время не учитывается.

Если остаток в течение дня ниже, чем на конец дня, это видно:
- **в ячейке дня** — строка «мин. −300 тыс. в 10:00» или «… с утра»
  (красным, если меньше нуля), с подсказкой;
- **в «Минимальном остатке в месяце»** и в колонке «Минимум в месяце»
  прогноза по счетам — с датой и временем («14.10.2026, в 10:00») или
  пометкой «на конец дня»;
- **в таблице «Прогноз по дням»** — новая колонка «Минимум в течение дня».

Код:
- `parseDueTime`, `showDueDate`, `compareDueTime`, `intradayLow` в
  `src/lib/payment-calendar.ts`; `buildMonthGrid` и `buildCalendarRows`
  отдают `lowWithinDay` и `lowTime`;
- перенос с временем — `rescheduleRequest`, `reschedulePart`,
  `rescheduleDocument` в `src/lib/payment-plan/service.ts`. Время не
  передано — остаётся прежнее. Одновременная правка проверяется по дате и
  времени.

Миграция `payment_due_time`: поле `dueTime` у заявок, частей графика и
документов начислений; `fromTime` и `toTime` в истории переносов.

- провал в сетке месяца и в таблице по дням;

## Дополнение после Этапа 7: валютные счета — курсы ЦБ, пересчёт в рубли, курсовые разницы; счёт оплаты части

**Валюта счёта и кассы** выбирается из списка: RUB, USD, EUR, CNY, KZT,
BYN, AED и другие. Раньше это был свободный текст.

**Справочник «Курсы валют»** (`/master-data/currency-rates`, модель
`CurrencyRate`) хранит курс в рублях за единицу валюты на дату.
- **Кнопка «Загрузить с сайта ЦБ»:** официальные курсы ЦБ РФ за период
  (до 5 лет за раз) для валют счетов и касс и отмеченных валют.
- **Ручной ввод:** курс можно ввести вручную. Загрузка из ЦБ такой курс не
  перезаписывает.
- **Какой курс берётся:** на дату — последний установленный не позже неё.
  Субботний курс действует в воскресенье и понедельник.
- **Автоматически:** планировщик вместе с выписками по API банков
  подгружает курсы за последнюю неделю, если сегодняшнего курса ещё нет
  (`ensureRecentRates` в `scripts/bank-sync.ts`).
- **Защита сайта ЦБ:** сайт отвечает 403 на серию быстрых запросов.
  Загрузчик делает паузу 1,5 с между запросами и повторяет при 403.
  Внутренние коды основных валют в ЦБ постоянные, поэтому лишний запрос
  списка не нужен.

**Как пересчитывается:**
- операция валютного счёта — в рублях по курсу на дату операции;
- остаток — по курсу на дату отчёта;
- разница — курсовая.

Где это видно:
- **ДДС:** поступления и выплаты по статьям — в рублях. Остаток на начало
  — по курсу на день до начала периода, на конец — по курсу на конец.
  Новый блок «Курсовая разница» с остатками в валюте, в выгрузке в Excel —
  строка «Курсовая разница». Остаток на конец = начало + поступления −
  выплаты + переводы + курсовая разница.
- **Управленческий баланс:** деньги — по курсу на дату баланса, авансы и
  статьи баланса — по курсам операций. Курсовые разницы входят в
  нераспределённую прибыль («по ОПиУ … + курсовые разницы …»), поэтому
  контрольное равенство сохраняется.
- **Дашборд:** остаток денег в рублях и строка «в т. ч. 800,00 $ по курсу
  ЦБ».
- **Платёжный календарь:** у валютного счёта остаток в его валюте и «≈ …
  ₽ по курсу ЦБ». Прогноз — в рублях, заявки и документы рублёвые.
- **Финансовые сценарии:** стартовый остаток — по курсу на сегодня.
  Доходы с начала года для налога — по курсам дат поступлений. Платежи по
  займам — в рублях.
- **Список операций** банка и кассы: сумма в валюте счёта (1 000,00 $).

Если курса на нужную дату нет, в отчёте предупреждение со ссылкой на
справочник. Сумма тогда берётся по ближайшему известному курсу, а если
курсов этой валюты нет совсем — как есть.

- В справочниках нет физического удаления. Архив и есть удаление: запись
  не предлагается в формах, из архива её можно вернуть кнопкой
  «Восстановить».
- Работает только в режиме «Обновлять изменившиеся поля».
- «Проверить без сохранения» показывает, сколько записей и какие уйдут в
  архив («Нет в файле — уйдёт в архив: …»).
- Записи, которые уже в архиве, не трогаются. Для записи, уходящей в
  архив, выполняется та же проверка справочника, что и при правке.
- **Защита от случайного файла:** если ни одна строка не совпала с
  записями справочника (другой справочник, пустой шаблон), загрузка
  остановится с ошибкой. Весь справочник разом в архив не уйдёт.
- Всё или ничего, одной транзакцией. В журнале аудита — число и ID
  отправленных в архив записей.
- Строки реквизитов и контактов контрагентов, которых нет в файле, по-прежнему
  не удаляются.

**Все ошибки за один проход.** Раньше при ошибке в ячейке загрузка
останавливалась до сопоставления строк. Дубли и неоднозначные ключи
становились видны только после исправления ячеек. Теперь строки с
ошибками в ячейках тоже сопоставляются с записями, но не сохраняются, и
все ошибки идут одним списком по порядку строк. Например, «Строка 2: «abc»
— не число» и «Строки 2 и 3 относятся к одной записи» показываются вместе.
Новые контрагенты из строк с ошибками учитываются и на листах реквизитов и
контактов, поэтому лишней ошибки «контрагент не найден» нет.

**Заодно:**
- справочники без текстового названия (курсы валют, производственный
  календарь) подписываются в сообщениях первыми полями: «USD ·
  2026-09-02», а не пустыми кавычками;
- в справке импорта для них вместо «по полям :» написано, что строка без ID
  всегда создаёт новую запись.

Код:
- `planImport` в `src/lib/dictionaries/import-plan.ts`: `archiveMissing`,
  `archives`, `pendingCreates`, строки с `invalid`;
- `parseImportRows` возвращает строки вместе с ошибками;
- `importDictionaryAction`.

Тесты: 4 новых (всего 427):
- архив отсутствующих — только по флажку и не в режиме «только добавлять»;
- записи, которые уже в архиве, не трогаются;
- защита от файла без совпадений;
- строка с ошибкой в ячейке всё равно находит дубль.

**Проверено в браузере** на трёх временных курсах валют: справочник был
пуст, записи рабочих справочников не затрагивались.

- Проверка файла с одной записью из трёх — «в архив (нет в файле): 2» со
