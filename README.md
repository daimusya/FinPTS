# ПРОМТЕХНОСФЕРА — Финансовая платформа

Многопользовательская платформа управленческого учёта: начисления и движение
денег отдельно, ДДС/ОПиУ/управленческий баланс, дебиторка/кредиторка,
зарплата, интеграции с 1С и Битрикс24, закрытие периодов. Источник истины —
серверная база данных PostgreSQL.

## Стек

- Next.js 16 (App Router) + TypeScript, React 19
- PostgreSQL + Prisma ORM (версионируемые миграции)
- Аутентификация: сессии на подписанных JWT (httpOnly cookie), bcrypt
- Server Actions как серверный API-слой; Route Handlers — для интеграций/экспорта
- Vitest — модульные тесты

## Запуск проекта локально

1. Установите зависимости:

   ```bash
   npm install
   ```

2. Скопируйте `.env.example` в `.env` и укажите строку подключения к
   PostgreSQL и `AUTH_SECRET` (длинная случайная строка).

3. Примените миграции и заполните начальные справочники:

   ```bash
   npm run db:migrate
   npm run db:seed
   ```

   Скрипт `db:seed` создаст роли, права и первого администратора (email
   берётся из `SEED_ADMIN_EMAIL` в `.env`, если не задан — `admin@example.com`).
   Временный пароль будет выведен один раз в консоль.

4. Запустите сервер разработки:

   ```bash
   npm run dev
   ```

   Приложение доступно на http://localhost:3000 и сразу открывает экран входа.

5. Тесты:

   ```bash
   npm test
   ```

## Развёртывание через Docker

Есть `Dockerfile` (многоступенчатая сборка, standalone-режим Next.js) и
`docker-compose.yml` (приложение + PostgreSQL). **Написано, но не
запускалось** в этой среде разработки — Docker здесь не установлен (сборка

хосте). Перед реальным использованием проверьте `docker compose up --build`
на своей машине.

Порядок:

```bash
export AUTH_SECRET=$(openssl rand -base64 32)
docker compose up -d postgres
# примените миграции и заполните справочники с хоста, указав на
# опубликованный порт контейнера (localhost:5432) — сознательно не
# выполняется автоматически при старте контейнера приложения, см. раздел
# «Правила выполнения задачи», п.8 ТЗ
DATABASE_URL="postgresql://promtehnosfera:promtehnosfera@localhost:5432/promtehnosfera" npm run db:migrate
DATABASE_URL="postgresql://promtehnosfera:promtehnosfera@localhost:5432/promtehnosfera" npm run db:seed
docker compose up -d app
```

Обязательные переменные окружения для продакшена: `DATABASE_URL`,
`AUTH_SECRET` (длинная случайная строка — используется и для подписи
сессий, и как ключ шифрования секретов интеграций, см. Этап 7).

## Реализовано (Этап 1: Фундамент)

- Полная схема данных в `prisma/schema.prisma`, покрывающая все домены из
  ТЗ: identity/access, master-data, accruals, cash-management,
  payments-matching, payroll, integrations, reporting, financial-modeling,
  period-close, audit.
- Аутентификация по email/паролю, сессии на JWT в httpOnly cookie.
- RBAC: 8 системных ролей, права настраиваются через
  «Администрирование → Роли и права» (создание ролей, изменение набора
  прав). Пользователи управляются через «Администрирование → Пользователи».
- Разграничение видимости по организациям/подразделениям/проектам
  (`UserOrganizationAccess`, `UserDepartmentAccess`, `UserProjectAccess`,
  `src/lib/access-scope.ts`) подключено к фильтрации данных. Принцип: «явное
  назначение — ограничение» — пока администратор не отметил пользователю ни
  одной организации/подразделения/проекта в «Администрирование →
  Пользователи → [пользователь] → Ограничение видимости», этот разрез
  остаётся неограниченным; полный администратор (`admin.full`) всегда видит
  всё в обход назначений. Подключено к: дашборду, списку документов
  начисления, банку/кассе, сотрудникам, расчётам зарплаты и всем пяти
  отчётам (ДДС, ОПиУ, управленческий баланс, маржинальность, дебиторка и
  кредиторка — включая выпадающий список организаций в фильтрах балансового
  отчёта и отчёта по задолженности). **Не подключено**: выгрузка в Excel
  (`/api/reports/export`), снимки закрытия периода и справочники-выпадашки
  в формах создания документов (создавая начисление, пользователь пока
  может выбрать любую организацию из списочника, а не только «свою») — эти
  места по-прежнему видят данные без ограничения по разрезу.
- Журнал аудита: все создания/изменения/архивирования справочников,
  вход/выход, закрытие и открытие периодов пишутся в `audit_log` и видны в
  «Администрирование → Журнал аудита».
- Учётные периоды: создание, ручное закрытие и повторное открытие с
  фиксацией пользователя и времени. Полный контрольный лист закрытия
  (проверка несопоставленных операций, незакрытых зарплатных расчётов и
  т.д. — раздел 17 ТЗ) — **не реализован**, это Этап 7.
- Справочники с реальным CRUD (создание, редактирование, архивирование —
  без физического удаления) и аудитом изменений:
  организации и ИП, подразделения, ЦФО, проекты, направления, продукты и
  услуги, контрагенты, договоры, статьи ДДС, статьи ОПиУ, статьи баланса.
  Начальные справочники (подразделения, направления, статьи) засеяны по
  тексту ТЗ.
- Дашборд показывает реальные счётчики из базы (организации, подразделения,
  контрагенты, проекты, сотрудники, открытые периоды). Финансовые
  показатели (ДДС, ОПиУ, баланс, маржинальность, точка безубыточности)
  сознательно не выводятся статичными значениями — они появятся на Этапе 3,
  когда будут построены начисления и банковские операции.

## Реализовано (Этап 2: Начисления и деньги)

- Документы начисления (`/accruals`): все 9 типов из ТЗ (счёт, акт, УПД,
  накладная, реализация, поступление, возврат, корректировка, ручное),
  многострочные, с аналитикой (подразделение, ЦФО, проект, продукт/услуга,
  статья ОПиУ) на уровне строки. Жизненный цикл черновик → проведён →
  отменён; редактировать можно только черновик; проведение и отмена
  проверяют, что учётный период открыт.
- Банковские счета и кассы как справочники; операции (`/cash/transactions`)
  вводятся вручную или загружаются из выписки.
- Универсальная загрузка банковской выписки (`/cash/import`): XLSX, XLS,
  CSV, TXT (TXT — автоопределение разделителя), ручное сопоставление
  колонок файла с полями операции (дата; сумма со знаком ИЛИ отдельные
  колонки прихода/расхода; назначение платежа; ИНН и наименование
  контрагента; номер операции банка), защита от повторной загрузки по
  fingerprint (композитный ключ счёт+дата+направление+сумма+назначение,
  либо номер операции банка, если он есть в файле), автоматическое
  определение контрагента по ИНН, протокол импортированных/дублей/ошибок.
  ~~Известное ограничение: без номера операции банка две операции с
  абсолютно одинаковыми счётом/датой/суммой/назначением могут быть
  ошибочно признаны дублем.~~ Исправлено — см. дополнение «Защита от
  дублей выписки без номера операции банка» в конце файла.
- Сопоставление банковских операций с начислениями (`/cash/transactions/[id]`):
  один платёж — один документ, один платёж — несколько документов
  (повторным сопоставлением остатка), несколько платежей — один документ;
  отмена сопоставления. Суммы считаются через `decimal.js`, без ошибок
  плавающей точки. Статусы оплаты документа (не оплачено / частично /
  оплачено / переплата) и сопоставления операции (не сопоставлено /
  частично / сопоставлено) пересчитываются автоматически.
- Дебиторская и кредиторская задолженность (`/reports/debts`): считается из
  проведённых непогашенных документов минус сопоставленные оплаты, с
  выделением просрочки по сроку оплаты.
- Платёжный календарь (`/payment-calendar`): текущий остаток по всем счетам
  и кассам (факт из банковских операций) + прогноз по срокам оплаты
  непогашенных начислений и согласованных заявок.
- Заявки на оплату (`/payment-requests`) с одноступенчатым согласованием
  (на согласовании → согласована/отклонена → оплачена), не полным
  настраиваемым маршрутом из раздела 9 ТЗ — это упрощение, отмеченное как
  ограничение ниже.
- Дашборд обновлён реальными показателями: остаток денег, дебиторка/
  кредиторка, просрочка, несопоставленные операции, согласованные заявки.

## Реализовано (Этап 3: Управленческая отчётность)

Всё в `src/lib/reports/` — чистые вычисления поверх сохранённых документов
и операций (без статичных цифр), с юнит-тестами на самую рискованную
арифметику (P&L-водопад, точка безубыточности, decimal-суммы).

- **ДДС** (`/reports/cash-flow`) — остаток на начало/конец периода,
  поступления и выплаты по статьям, внутренние переводы отдельной строкой.
  Остаток на начало периода считается как сумма всех операций до начала
  периода (а не через отдельно хранимый остаток на счёте).
- **ОПиУ** (`/reports/pnl`) — выручка → валовая прибыль → операционная
  прибыль → чистая прибыль по методу начисления, с разбивкой по статьям и
  сравнением с предыдущим месяцем. Считается только из проведённых
  документов.
- **Управленческий баланс** (`/reports/balance`) — денежные средства и
  задолженность из фактических данных; авансы, зарплата к выплате, займы,
  капитал и прочие активы — см. дополнение «Управленческий баланс: авансы,
  займы, капитал и остатки» в конце файла (изначально были равны нулю).
  **Контрольное равенство**: «Активы − Обязательства» сверяется с
  накопленной чистой прибылью по ОПиУ, расхождение показывается как
  диагностика с объяснением вероятной причины, а не скрывается.
- **Маржинальность и точка безубыточности** (`/reports/margin`) — валовая
  прибыль, точка безубыточности (Постоянные затраты / Доля маржинального
  дохода), запас финансовой прочности, разбивка по проектам, продуктам/
  услугам и клиентам. Распределение косвенных расходов по этим разрезам —
  настраиваемый драйвер, см. дополнение после Этапа 7 ниже.
- **Фильтры**: период (год/месяц), организация, подразделение, ЦФО,
  проект, продукт/услуга, контрагент — на каждом отчёте.
- **Расшифровка до документа**: клик по статье в ДДС/ОПиУ открывает список
  операций/документов, отфильтрованный именно по этой статье и периоду.
- **Excel-экспорт** (`/api/reports/export`) — ДДС, ОПиУ, задолженность,
  управленческий баланс. Экспорт применяет то же ограничение видимости по
  организациям/подразделениям/проектам, что и сами отчёты на экране.
- Дашборд дополнен показателями текущего месяца: выручка, валовая/
  операционная/чистая прибыль, рентабельность.

## Реализовано (Этап 4: Интеграции)

- **1С — файловый обмен** (`/integrations/1c`): импорт документов начисления
  из табличной выгрузки (XLSX/CSV/TXT — XML/JSON из ТЗ не поддержаны, см.
  ограничение ниже), ручное сопоставление колонок, шаблон файла для
  скачивания. **Идемпотентно**: строка с уже известным внешним ID 1С
  обновляет существующий документ, а не создаёт дубль — проверено
  сценарием «импорт → повторный импорт того же файла → импорт с изменённой
  суммой» с автоматической сверкой количества документов и итоговой суммы.
  Организация ищется по ИНН (создать нельзя — ошибка, если не найдена);
  контрагент ищется по ИНН и автоматически создаётся, если не найден
  (с пометкой `dataSource: "1C"`). Строка с датой в закрытом периоде или
  несуществующей организацией/статьёй не прерывает импорт — уходит в
  очередь ошибок с понятным сообщением, видна в журнале синхронизации
  (`/integrations/1c/batches/[id]`) вместе со счётчиками создано/
  обновлено/ошибок. Прямой обмен через HTTP/OData — не реализован
  (нет адреса публикации и учётных данных), как и требует ТЗ.
- **Битрикс24 — outbox** (`/integrations/bitrix24`): при каждом изменении
  статуса оплаты проведённого документа начисления (сопоставление платежа

  `payment_status_changed` с суммой задолженности и признаком просрочки.

  «Ожидает отправки», попытки не растрачиваются впустую. Реальная отправка
  проверена на неотвечающем URL: статус корректно переходит в «Ошибка»,
  попытка и текст ошибки записываются.

## Реализовано (Этап 6: Финансовое моделирование)

- **Сценарии** (`/financial-model`): базовый/оптимистичный/пессимистичный/
  пользовательский, любое количество. Прогноз строится на 12 месяцев от
  выбранного старта (по умолчанию — текущий месяц), стартовая точка
  остатка денег — реальный фактический остаток по банковским/кассовым
  операциям на сегодня (не выдуманное число).
- **Драйверы**: средний чек, количество продаж, сезонность, корректировка
  базовой выручки (изначально — «активация новых услуг»; новые услуги
  теперь задаются списком, см. дополнение «Новые услуги в финансовых
  сценариях»), доля продаж через посредников и их комиссия, переменные
  расходы (% от выручки), постоянные расходы, средняя стоимость
  сотрудника в месяц, платежи по кредитам/лизингу/отсрочкам — все
  редактируются помесячно в одной таблице-редакторе. Пустая ячейка
  означает «не задано», а не 0: для сезонности и корректировки выручки
  это трактуется как 100% (по умолчанию не искажает прогноз), для
  остальных драйверов — как 0.
- **Производительность на сотрудника отдельно по подразделениям**
  (обязательное требование ТЗ, минимум для отдела обучения и охраны
  труда — эти два подразделения подставляются в редактор по названию,
  если их переименовали — берутся первые доступные): для каждого
  подразделения задаются продажи и производительность на сотрудника,
  система считает **требуемую численность = продажи / производительность
  (с округлением вверх)** и суммирует с вручную заданной численностью
  прочего персонала.
- **Прогноз**: выручка → переменные расходы → комиссия посредников →
  валовая прибыль → постоянные расходы + ФОТ → операционная прибыль,
  точка безубыточности и запас финансовой прочности (переиспользуют
  формулы Этапа 3), остаток денег помесячно нарастающим итогом с учётом
  платежей по кредитам.
- **Сравнение сценариев** (`/financial-model/compare`): любое количество
  сценариев бок о бок — выручка, операционная прибыль, остаток денег на
  конец горизонта, средняя точка безубыточности за 12 месяцев.

Проверено сквозным сценарием через реальный UI (не напрямую через БД):
создал сценарий → ввёл средний чек 1000, продажи 100, переменные 30%,
постоянные 20 000, продажи/производительность по двум подразделениям
(55/20 и 40/20) → сохранил → прогноз показал ровно то, что предсказывает
формула: выручка 100 000, численность 5 (3+2, округление вверх),
операционная прибыль −25 000, точка безубыточности 135 714,29, запас
прочности −35,71% — до копейки. Сравнение двух сценариев отобразило
правильные значения бок о бок. Тестовые данные удалены.

При проверке через браузер нашёл и исправил баг в самом тестовом
сценарии использования (не в приложении): `document.querySelector('form')`
в моём тестовом JS-скрипте попадал на форму выхода из системы в шапке
(она в DOM раньше формы страницы) и разлогинивал сессию вместо создания
сценария — после уточнения селектора (`input.closest('form')`) всё
заработало. Также обнаружил и исправил реальный баг в схеме: Prisma не
поддерживает `null` в составном уникальном ключе (`FinancialScenarioValue`
на `[scenarioId, year, month, driver, dimension]`) — заменил
`dimension String?` на `dimension String @default("")` с пустой строкой
как сентинел для «без подразделения» (миграция
`financial_scenario_dimension_default`).

## Реализовано (Этап 7: Закрытие месяца и production-готовность)

### Контрольный лист закрытия периода

`/admin/periods/[id]/close` — все 9 проверок из раздела 17 ТЗ, реально
запрашивают базу (не заглушки):

1. Необработанные документы 1С (импорты с ошибками) — **критично**
2. Ошибки и конфликты интеграций — **критично**
3. Документы без обязательной аналитики (строка начисления без статьи
   ОПиУ) — **критично**
4. Несопоставленные банковские операции за период — предупреждение
5. Незавершённые зарплатные расчёты за период (не «утверждён»/«выплачен»)
   — **критично**
6. Несогласованные заявки на оплату со сроком в периоде — предупреждение
7. Расхождения управленческого баланса (контрольное равенство из Этапа 3)
   — предупреждение
8. Непроведённые (черновик) документы начисления за период —
   предупреждение
9. Дубли банковских операций по отпечатку — предупреждение (структурно
   не должно случаться, т.к. защищено уникальным индексом при загрузке)

Критические ошибки **блокируют** закрытие — кнопки «Закрыть период» нет,
пока они не исправлены. Предупреждения требуют явной галочки «Я
ознакомился и осознанно закрываю период». Результаты каждой проверки
сохраняются в `period_close_checks` при каждой попытке закрытия (даже
неудачной) — это часть истории периода, видна в списке периодов рядом с
датой закрытия.

При успешном закрытии фиксируется **снимок контрольных показателей**
(`AccountingPeriod.closingSnapshot`): остаток денег на начало/конец
периода, выручка, чистая прибыль, дебиторка, кредиторка, активы,
обязательства, расхождение баланса — на момент закрытия, не
пересчитывается задним числом при последующих изменениях. Показан в
списке периодов по клику.

Закрытый период запрещает изменение документов везде, где это уже было
реализовано на предыдущих этапах (`assertPeriodOpenForDate` в
начислениях, банковских операциях, зарплате) — проверено вживую: критичная
ошибка (незавершённый расчёт зарплаты) корректно заблокировала закрытие
периода без кнопки закрытия.

### Безопасность

Заказал отдельный агентский аудит безопасности по чек-листу раздела 22 ТЗ
(RBAC на каждом действии, SQL-инъекции, XSS, CSRF, секреты в коде,
безопасность загрузки файлов, утечка технических деталей в ошибках,
конфигурация cookie). Нашлось два реальных замечания, оба исправлены:

- **Временный пароль передавался в query-параметре URL** при создании
  пользователя/сбросе пароля — оседал в логах доступа, истории браузера,
  заголовке Referer. Заменено на одноразовую httpOnly-куку
  (`src/lib/flash.ts`, TTL 60 секунд), пароль в URL больше не попадает.
- **Вебхук Битрикс24 хранился в БД открытым текстом** (в его URL зашит
  токен доступа) — теперь шифруется AES-256-GCM с ключом, производным от
  `AUTH_SECRET` (`src/lib/crypto/secret-box.ts`), в форме показывается
  только маска (первые 8 и последние 4 символа).

Остальные пункты чек-листа (RBAC на каждом действии, безопасность
загрузки файлов, отсутствие сырых SQL-конкатенаций, отсутствие секретов в
репозитории, конфигурация cookie, отсутствие `dangerouslySetInnerHTML`)
прошли проверку без замечаний — подробности в истории коммита.

## Дополнение после Этапа 7: настраиваемый многошаговый маршрут согласования заявок на оплату

Реализован раздел «Администрирование → Маршруты согласования»

проходит одноступенчатое согласование» из раздела 9 ТЗ.

- Маршрут — упорядоченный список шагов, каждый шаг требует согласования от
  конкретной **роли** (не пользователя — так маршрут не привязан к
  конкретному человеку). Маршрут применяется к заявке, если сумма попадает
  в заданный диапазон (границы включительно, пусто — без ограничения) и

  заявки и хранится на ней (`routeId`) — правки маршрута после создания
  заявки на уже созданные заявки не переносятся сами по себе, но **правки
  списка шагов существующего маршрута повлияют на заявки, уже идущие по
  нему** (шаг может исчезнуть или роль — измениться), это явно
  зафиксировано как ограничение на странице редактирования маршрута.
- Согласование шага требует членства именно в роли этого шага (проверяется

  системе. Заявка без маршрута по-прежнему требует общего права.
- Чистая логика выбора маршрута и шагов — `src/lib/payment-requests/approval.ts`,

## Дополнение после Этапа 7: автопроводка начисленной зарплаты в ОПиУ

При утверждении расчёта зарплаты (кнопка «Утвердить», переход

  привязана, документ вообще не создаётся, и страница расчёта явно

## Дополнение после Этапа 7: защита от дублей выписки без номера операции банка

Если в выписке нет номера операции банка, строка опознаётся по счёту,
дате, направлению, сумме и назначению платежа. Раньше две настоящие, но
одинаковые операции (например, две комиссии по 150 ₽ за перевод в один
день) давали один и тот же отпечаток — вторая молча считалась дублем и
терялась. Теперь отпечатки считаются по всему файлу сразу, и одинаковые
строки нумеруются в порядке появления:

- первая получает прежний отпечаток — поэтому уже загруженные ранее
  операции и операции, введённые вручную, по-прежнему опознаются как
  дубли; вторая — отпечаток с пометкой «#2», третья — «#3» и т.д.;
- повторная загрузка того же файла даёт те же номера — все строки
  отсекаются как дубли;
- выписка, перекрывающая уже загруженную (например, сначала выписка за
  часть дня, потом за весь день), тоже обрабатывается верно: известные
  операции отсекаются, новые одинаковые загружаются, порядок остальных
  строк в файле не важен;
- строки с номером операции банка не нумеруются: один номер дважды — это
  одна и та же операция.

Протокол загрузки сообщает, сколько строк загружено как повторы уже
встречавшейся в файле операции. Чистая логика —
`computeStatementFingerprints` (`src/lib/bank-import/fingerprint.ts`),
6 юнит-тестов.

Проверено в браузере: выписка с двумя одинаковыми комиссиями и платежом →
загружено 3 (раньше было бы 2 и «1 дубль»); та же выписка повторно →
0 загружено, 3 дубля; выписка за полный день с третьей такой же комиссией
и новой арендой (в другом порядке строк) → 2 загружено, 3 дубля. В базе —
ровно 3 комиссии, платёж и аренда, даты верные.

- **Ограничение**: нумерация опирается на то, что каждая выписка содержит
  день целиком или его начало. Если загрузить сначала выписку, где из двух
  одинаковых операций дня есть только вторая (банк выгрузил день не с
  начала), а затем полную — первая из них будет признана дублем. На
  практике банки выгружают выписки целыми днями.
- Ручной ввод операции (`/cash/transactions/new`) по-прежнему не даёт
  ввести вторую полностью одинаковую операцию в тот же день на тот же
  счёт — там это защита от двойного нажатия; при необходимости достаточно
  чуть изменить назначение платежа.

## Дополнение после Этапа 7: бюджет и план-факт в ДДС и ОПиУ

Новый раздел «Моделирование → Бюджет (план)» (`/budget`) — помесячный план
по статьям: бюджет движения денежных средств (БДДС, статьи ДДС) и бюджет
доходов и расходов (БДР, статьи ОПиУ). Финансовые сценарии Этапа 6 для
этого не подходят: они считают прогноз из драйверов (средний чек, доля
переменных расходов и т.д.), а не по статьям, и сравнить их построчно с
отчётами нельзя.

- **Редактор** — сетка «статья × 12 месяцев» на выбранный год, с итогами по
  разделам и за год. План задаётся либо по компании в целом, либо по
  конкретной организации. Суммы положительные (направление определяет
  статья); пустая ячейка — «плана нет», 0 — «запланирован ноль». Статьи
  переводов между своими счетами в бюджет не входят. Архивные статьи
  показываются, только если по ним уже есть план. Сохранение — вся сетка
  года одной транзакцией, с записью в журнал аудита; неверная сумма
  отсекается ещё в браузере, а на сервере — повторно, и тогда не
  сохраняется ничего. Права: просмотр — `financial_model.view`,
  изменение — `financial_model.manage` (те же, что у сценариев);
  пользователь с доступом только к части организаций видит и правит план
  только своих организаций.
- **ДДС** (`/reports/cash-flow`): при наличии плана на месяц в таблицах
  поступлений и выплат появляются колонки «План», «Отклонение» (факт −
  план) и «Исполнение», строка «Итого» и плановые суммы в карточках.
- **ОПиУ** (`/reports/pnl`): в фильтре «Сравнить с» — предыдущим месяцем
  (как раньше, по умолчанию) или планом. В режиме плана — те же колонки по
  статьям и разделам, плюс строки валовой, операционной и чистой прибыли
  по плану.
- Статья, по которой есть план, но нет факта, всё равно показывается —
  с нулевым фактом, иначе невыполненный план было бы не видно.
- Отклонение подсвечивается по смыслу, а не по знаку: зелёным — в пользу
  компании (больше поступлений и доходов, меньше выплат и расходов),
  красным — нет.
- Какой план берётся: без фильтра по организации — план компании в целом
  плюс планы всех организаций; с фильтром — только план этой организации;
  при доступе, ограниченном частью организаций, — только их планы. При
  фильтре по подразделению, ЦФО, проекту, продукту или контрагенту (и при
  доступе, ограниченном подразделениями/проектами) сравнение с планом не
  показывается, и отчёт объясняет почему: факт в этом случае — лишь часть
  статьи, а план задан на статью целиком.
- Экспорт ДДС и ОПиУ в Excel включает колонки плана по тем же правилам.
- Новая таблица `BudgetEntry` (миграция `add_budget_entries`). Чистая
  логика — `src/lib/budget/plan-fact.ts`, 11 юнит-тестов.

Проверено в браузере на сентябре 2026: факт ДДС — поступления 120 000,
оплата поставщикам 50 000; план по компании в целом, введённый через
редактор, — поступления 100 000, оплата поставщикам 50 000, налоги 20 000.
Отчёт: поступления +20 000 (120 %, зелёным), оплата поставщикам 0 (100 %),
налоги −20 000 (0 %, зелёным — статья без факта показана), итого выплаты

расходы 50 000; план по организации — 250 000 и 40 000. Отчёт: выручка
−50 000 (80 %, красным), косвенные +10 000 (125 %, красным), операционная и
чистая прибыль 150 000 против 210 000 (71,43 %). Совпало с ручным расчётом;
выгрузки в Excel дали те же числа. Фильтр по организации без её плана и
фильтр по контрагенту показывают пояснение вместо колонок плана;
отрицательная сумма, отправленная в обход браузерной проверки, отклонена
сервером без сохранения.

- **Не реализовано**: план по подразделениям, ЦФО и проектам (только по
  компании и организациям); план за квартал или год — отчёты помесячные;
  загрузка плана из Excel и копирование плана с прошлого года; план в
  управленческом балансе и маржинальности. План можно менять и для
  закрытых периодов — это не учётные данные, но изменения видны в журнале
  аудита.

## Дополнение после Этапа 7: отпускные и больничные по среднему заработку

На странице расчёта зарплаты (черновик или рассчитанный) появился блок
«Отпускные и больничные по среднему заработку»: выбрать сотрудника, дату
начала, число календарных дней — система показывает подробную расшифровку
и по кнопке добавляет строку «Отпускные» или «Больничные» в расчёт (с
НДФЛ, взносами и разнесением по проектным долям сотрудника, как у
автоматического расчёта). Сумма при добавлении пересчитывается на
сервере заново — из формы берутся только параметры. Каждая такая строка
пишется в журнал аудита вместе с расшифровкой (средний дневной заработок,
дни расчётного периода и т.д.).

- **Откуда берётся заработок**: только утверждённые и выплаченные
  расчёты — черновики ещё могут измениться. Заработок относится к месяцу,
  за который начислен: окончательный расчёт 10-го — к предыдущему месяцу,
  аванс и разовые выплаты — к месяцу выплаты.
- **Отпускные** (ст. 139 ТК РФ, Положение № 922): начисления видов с
  отметкой «учитывается в среднем заработке» за 12 календарных месяцев
  перед месяцем начала отпуска. Дни: 29,3 за полностью отработанный месяц,
  29,3 / дней в месяце × отработанные календарные дни — за неполный.
  Исключаются дни до приёма на работу и дни отпуска, болезни и
  командировок по табелю. Средний дневной заработок × дни отпуска. Если в
  расчётном периоде нет ни заработка, ни отработанных дней, — по окладу
  (оклад / 29,3).
- **Больничные** (ст. 14 Закона № 255-ФЗ): выплаты, облагаемые взносами,
  за два календарных года перед годом болезни, плюс заработок у других
  работодателей по справкам (вводится в форме); каждый год — не больше
  предельной базы. Сумма / 730, но не меньше МРОТ × 24 / 730; × 60/80/100%
  по страховому стажу (выбирается в форме — данных о стаже у прежних
  работодателей в системе нет). В расчёт попадают первые 3 дня — их платит
  работодатель; остальное Социальный фонд выплачивает напрямую, это
  показано в расшифровке.
- **Новый справочник «Параметры расчёта зарплаты»**
  (`/master-data/payroll-parameters`): предельная база для страховых
  взносов по годам (2021–2026) и МРОТ на 1 января (2023–2026) заполнены
  миграцией `add_payroll_parameters`; значения на следующие годы
  добавляются там же. Если нужного года нет, расчёт прямо об этом говорит.
- Попутно: дубль уникального поля в любом справочнике (код вида
  начисления, параметр за тот же год) раньше давал ошибку 500 — теперь
  понятное сообщение; при импорте из Excel — так же.
- Чистая логика — `src/lib/payroll/average-earnings.ts`, 8 юнит-тестов
  (полный год, приём в середине месяца + больничный, расчёт по окладу,
  предельная база, минимум по МРОТ, нет параметра за год).

Проверено на данных: сотрудник принят 01.03.2025 с окладом 100 000,
выплаченные аванс и окончательный расчёт за каждый месяц по август 2026,
премия 30 000 в июне, больничный 11–15 мая по табелю (и пособие за него),
а также черновик с премией 1 000 000. Отпуск с 14.09.2026 на 14 дней:
заработок 1 230 000, дней 346,874 (в мае 24,574 — пять дней болезни
исключены), средний 3 545,95, отпускные 49 643,30 — совпало с ручным
расчётом; черновик и пособие по болезни в заработок не попали. Больничный
с 15.09.2026 на 5 дней, стаж 80%, 800 000 у прежнего работодателя за
2024: средний 2 465,75, пособие 1 972,60 в день, всего 9 863,00, из них
работодатель — 5 917,80 (3 дня), Социальный фонд — 3 945,20.

- **Не реализовано**: индексация среднего заработка при повышении окладов
  (п. 16 Положения № 922); ограничение пособия одним МРОТ в месяц при
  стаже меньше 6 месяцев; районные коэффициенты; замена лет расчётного
  периода для больничных по заявлению сотрудника; учёт страхового стажа

## Дополнение после Этапа 7: оклад и аванс по табелю и производственному календарю

Автоматический расчёт зарплаты больше не платит фиксированную долю оклада:

- **Оклад за месяц** (окончательный расчёт 10-го числа) = оклад ×
  отработанные рабочие дни / норма рабочих дней месяца; к выплате — минус
  аванс, выплаченный 25-го.
- **Аванс** (25-го числа) = оклад × отработанные рабочие дни с 1 по 15
  число / норма рабочих дней месяца — ст. 136 ТК РФ требует платить аванс
  за фактически отработанное время. В месяце без отсутствий это примерно
  половина оклада (в сентябре 2026 — ровно 11 из 22 дней), а не всегда
  ровно 50%.
- **Табель ведётся «по отклонениям»**: рабочий день без отметки считается
  отработанным (пустой табель — полный оклад, как раньше). Не отработан —
  день с отметкой «Отпуск», «Больничный», «Командировка» или «Отсутствие»,
  если в тот же день нет отметки о работе. Отпуск и больничный оплачиваются
  отдельно по среднему заработку (см. предыдущее дополнение). Дни до приёма
  и после увольнения не оплачиваются.
- **Норма рабочих дней** — по новому справочнику «Производственный
  календарь» (`/master-data/production-calendar`): хранятся только
  отклонения от пятидневки (нерабочие будние дни — праздники и переносы, и
  рабочие субботы). Календарь на 2025 и 2026 годы заполнен миграцией; нормы,
  которые из него следуют, сверены с официальными в юнит-тестах: 247
  рабочих дней в 2025 и в 2026 году, январь 2026 — 15, май 2026 — 19,
  ноябрь 2025 — 19 (с рабочей субботой 1 ноября). Если календарь на год не
  заполнен, расчёт не выполняется и говорит об этом прямо — старые строки
  расчёта при этом не удаляются.
- Каждая автоматическая строка показывает, как получена сумма: «Отработано
  17 из 22 раб. дн. месяца (отпуск 5); оклад за месяц 85000.00 минус аванс
  45000.00». Строки отпускных и больничных по среднему заработку — тоже
  (средний дневной × дни). Новое поле `PayrollLine.comment` (миграция
  `production_calendar_and_line_comment`).
- Массовое заполнение табеля с галочкой «Пропускать выходные и праздники»
  теперь пропускает и праздники по производственному календарю.
- **Исправлена ошибка табеля**: массовое заполнение без проекта (обычный
  случай — отпуск, больничный, рабочие дни) падало с ошибкой 500: код
  использовал `upsert` по составному ключу с `projectId`, а Prisma не
  принимает в нём `null` (та же проблема, что с `FinancialScenarioValue`
  на Этапе 6). Заменено на «найти — обновить или создать».
- Чистая логика — `src/lib/payroll/work-calendar.ts`, 7 юнит-тестов.

Проверено через интерфейс на сентябре 2026 (норма 22 дня), оклад 110 000:
у сотрудника в штате с 2020 года отпуск 12–20 сентября отмечен в табеле
(5 рабочих дней, из них 14 и 15 — в первой половине месяца); вторая
сотрудница принята 16 сентября. Аванс 25.09: первому — 9 из 22 дней =
45 000, второй — ничего (ещё не работала). Окончательный расчёт 10.10:
первому — 17 из 22 = 85 000 минус аванс 45 000 = 40 000, второй — 11 из
22 = 55 000. Заполнение табеля 2–6 ноября с пропуском праздников создало
4 дня (4 ноября пропущено). Аванс за январь 2027 года (календарь не
заполнен) — понятная ошибка, расчёт не тронут.

- **Не реализовано**: сменные графики и суммированный учёт (норма — по
  пятидневке; справочник «Графики работы» пока только название);
  оплата работы в выходные и праздники в повышенном размере и
  сверхурочных (ст. 152–153 ТК РФ); сокращённые предпраздничные дни
  (важны для почасовой оплаты, для оклада по дням — нет); командировка
  по среднему заработку считается отдельной строкой вручную.

## Дополнение после Этапа 7: новые услуги в финансовых сценариях

Раздел 15 ТЗ хочет новые услуги списком с датой запуска, а драйвер
«активация новых услуг» был одним общим множителем на выручку. Теперь в
каждом сценарии есть блок «Новые услуги» (`/financial-model/[id]`):

- Услуга: название (или выбор из справочника «Продукты и услуги» —
  тогда название берётся оттуда), месяц запуска, средний чек, продажи в
  месяц на полной мощности, за сколько месяцев услуга выходит на полную
  мощность (0 — сразу) и, при необходимости, свои переменные расходы в %.
- С месяца запуска услуга добавляет к выручке: средний чек × продажи ×
  доля выхода на мощность × сезонность сценария. Выход на мощность —
  линейный: при 3 месяцах — 1/3 объёма в месяц запуска, 2/3 во втором,
  полный объём с третьего. Переменные расходы — свой % услуги или % сценария;
  комиссия посредников считается со всей выручки, включая новые услуги.
- В прогнозе выручка разложена на базовую (драйверы) и по каждой новой
  услуге; то же — в выгрузке прогноза в Excel. В сравнении сценариев
  добавлена строка «в т.ч. новые услуги».
- Прежний драйвер оставлен и переименован в «Корректировку базовой
  выручки»: это тот же множитель, поэтому у существующих сценариев цифры
  не меняются, но он больше не выдаёт себя за «новые услуги» и на новые
  услуги не влияет.
- Добавление и удаление услуг пишется в журнал аудита. Таблица
  `FinancialScenarioNewService` (миграция `scenario_new_services`).
- Попутно: страница сравнения сценариев брала стартовый остаток денег
  собственной копией расчёта без учёта ограничения видимости по
  организациям — теперь использует общий `getCurrentCashBalance(scope)`, как
  страница сценария.
- Чистая логика — `projectScenario`/`rampShare`
  (`src/lib/financial-model/project.ts`) и проверка формы
  (`src/lib/financial-model/new-services.ts`), 8 новых юнит-тестов.

Проверено через интерфейс: сценарий с базовой выручкой 200 000 в месяц
(чек 10 000 × 20) и переменными расходами 30%, прогноз с октября 2026.
Добавлены «Аудит СОУТ» (запуск декабрь 2026, чек 45 000, 4 продажи,
выход на мощность за 3 месяца) и услуга из справочника без ввода названия

Прогноз: СОУТ — 60 000 в декабре, 120 000 в январе, 180 000 с февраля;

## Дополнение после Этапа 7: автоматическое резервное копирование

Раньше была только ручная команда в README. Теперь:

- **`npm run db:backup`** (`scripts/backup.mjs`, работает на Windows и Linux):
  `pg_dump` в сжатом формате custom во временный файл с переименованием
  после успеха (незавершённая копия никогда не выглядит готовой); проверка,
  что архив читается и в нём есть таблицы (`pg_restore --list`); ротация —
  хранятся `BACKUP_KEEP` последних копий (по умолчанию 14), удаляются только
  файлы копий этой базы, ручные файлы в папке не трогаются. Пароль передаётся
  через `PGPASSWORD`, а не в командной строке. На Windows `pg_dump`
  находится сам в `C:\Program Files\PostgreSQL\<версия>\bin` (или
  `PG_BIN_DIR`).
- **`npm run db:backup:verify`** — то же плюс настоящее пробное
  восстановление: копия разворачивается во временную базу
  `<имя>_restore_check`, число строк сверяется по всем таблицам, временная
  база удаляется. Только так можно знать, что из копии действительно
  восстановимся.
- **Журнал**: каждый запуск пишется в таблицу `backup_runs` (миграция
  `backup_runs`) и строкой в `backups/backup.log` — последнее работает
  и когда сама база недоступна. Код выхода 1 при ошибке — планировщик видит
  сбой. Сообщения PostgreSQL выводятся по-английски: на Windows локализованные
  сообщения приходят в кодировке ANSI и превращались в «кракозябры».
- **Страница «Администрирование → Резервные копии»** (только полный
  администратор): когда была последняя успешная копия, история запусков
  (размер, число таблиц, результат пробного восстановления, ошибки) и
  предупреждение, если успешной копии нет дольше 26 часов.
- **`/api/health`** теперь сообщает свежесть копии
  (`backup: { state: ok | stale | never }`) — внешний монитор может
  предупредить о пропущенном бэкапе. Сам ответ при этом остаётся 200: приложение
  работает.
- **Расписание**:
  - Windows — `powershell -ExecutionPolicy Bypass -File scripts\register-backup-task.ps1`
    регистрирует ежедневную задачу в Планировщике заданий (по умолчанию 03:00,
    `-Time 23:30` — другое время, `-Remove` — удалить); если компьютер
    был выключен, копия делается при следующем включении. Задача запускает
    `scripts\run-backup.cmd` (копия с пробным восстановлением, вывод — в
    `backups\scheduler.log`).
  - Linux — строка в crontab: `0 3 * * * cd /путь/к/проекту && npm run db:backup:verify`.
  - Docker — сервис `backup` в `docker-compose.yml` (`Dockerfile.backup`:
    Node + клиент PostgreSQL 17, копии в томе `backups`, раз в сутки).
    **Написано, но не собиралось** — Docker в этой среде не установлен, как и
    для основного образа.
- **Безопасность**: папка `backups/` добавлена в `.gitignore` и
  `.dockerignore` — копии содержат персональные данные и не должны попасть ни
  в репозиторий (он публичный), ни в образ контейнера.
- Восстановление (затирает текущие данные — сначала остановите приложение):
  `pg_restore --clean --if-exists --no-owner --dbname promtehnosfera backups/<файл>.dump`.
  Безопаснее восстановить в новую базу, проверить и переключить на неё
  `DATABASE_URL`.
- Чистая логика — `scripts/backup-core.mjs` (разбор `DATABASE_URL`, имя
  файла, выбор копий на удаление, сверка строк) и `src/lib/backup/status.ts`
  (свежесть), 8 юнит-тестов.

Проверено на этой машине (PostgreSQL 17): копия 155 КБ, 61 таблица;
пробное восстановление — 61 таблица, 288 строк, совпадает с базой,
временная база удалена; при `BACKUP_KEEP=2` удалена ровно одна старая
копия, ручной файл в папке остался; ненайденный `pg_dump` и недоступная
база — код выхода 1, понятная запись в журнале; обёртка для Планировщика
отработала; страница показала историю, а при искусственно «состаренной»
последней копии (30 ч) — предупреждение, и `/api/health` вернул `stale`.

- **Не сделано**: сама задача в Планировщике на этом компьютере не
  зарегистрирована — это постоянное изменение настроек системы, его нужно
  подтвердить (одна команда выше). Копии хранятся на том же диске, что и
  база: перенос в другое место (облако, другой сервер) нужно настроить
  отдельно — это защита от потери диска, а не от ошибок в данных.
  Кнопки «сделать копию сейчас» в веб-интерфейсе нет сознательно: веб-сервер
  не должен запускать `pg_dump` и писать файлы копий.

## Дополнение после Этапа 7: управленческий баланс — авансы, займы, капитал и остатки

Раньше в балансе авансы, зарплата к выплате, займы, капитал и прочие
активы были жёстко равны нулю, поэтому контрольное равенство почти всегда
показывало расхождение. Теперь:

- **Авансы** считаются сами: платёж контрагенту, не сопоставленный с
  документами начисления, — аванс выданный (актив); такое же поступление —
  аванс полученный (обязательство). Не авансы: переводы между своими
  счетами, операции без контрагента и операции по статьям ДДС, привязанным
  к статье баланса.
- **Налоги и зарплата к выплате** — непогашенная часть документов
  автопроводки расчётов зарплаты, отдельно от обычной кредиторки.
- **Займы, капитал, прочие активы** и любые свои статьи баланса:
  - статью ДДС можно привязать к статье баланса (справочник «Статьи ДДС»,
    поле «Статья баланса»): получение кредита увеличивает «Займы и
    кредиты», погашение — уменьшает; взнос учредителя — «Капитал»; покупка
    оборудования — «Прочие активы» (за актив деньги платят, поэтому выплата
    его увеличивает);
  - **балансовые операции** на странице баланса — ручной ввод остатков на
    начало учёта и корректировок (сумма со знаком, дата, организация или
    вся компания, комментарий), с удалением; закрытый период их не
    принимает, всё пишется в журнал аудита.
- Строки, которые баланс считает из операций (деньги, дебиторка, авансы,
  кредиторка, зарплата к выплате), помечены в справочнике статей баланса
  системным кодом — по ним нельзя вводить операции и привязывать статьи ДДС,
  иначе суммы задвоятся. Нераспределённая прибыль считается по ОПиУ, но
  принимает операции — для прибыли прошлых лет на начало учёта.
- Контрольное равенство осталось диагностикой, но теперь указывает на
  реальные пробелы — деньги, прошедшие мимо и документов, и статей баланса
  (комиссия банка без документа, неучтённый остаток и т.п.); подсказка на
  странице перечисляет типичные причины. Экспорт в Excel — с новыми строками.
- Новое: `BalanceArticle.systemCode`, `CashFlowArticle.balanceArticleId`,
  таблица `BalanceEntry` (миграция `management_balance`; семя проставляет
  системные коды и на новой базе). Чистая логика —
  `src/lib/reports/balance-lines.ts`, 7 юнит-тестов.

Проверено через интерфейс: взнос учредителя 10 000, кредит 500 000 и его
погашение 50 000, покупка оборудования 100 000, предоплата клиента 30 000
без счёта, неоплаченный счёт 200 000, неоплаченное начисление зарплаты
65 100. Баланс: деньги 390 000, дебиторка 200 000, займы 450 000, капитал
10 000, аванс полученный 30 000, зарплата к выплате 65 100, прибыль
134 900 — равенство выполняется. Пока статья «покупка оборудования» не была
привязана, 100 000 стояли авансом выданным; после привязки через форму
справочника (в списке только статьи, допускающие изменение) — в «Прочих
активах». Две балансовые операции по 20 000 (оборудование и капитал) —

Комиссия банка 500 без контрагента дала ровно −500 расхождения; баланс на
05.09 учёл только операции от 01.09; выгрузка Excel совпала с экраном;
удаление операции работает. Тестовые данные удалены.

- **Не реализовано**: сопоставления платежей берутся текущие, поэтому баланс
  на прошлую дату считает дебиторку и авансы по сегодняшнему состоянию
  сопоставлений; амортизация основных средств и проценты по займам
  автоматически не начисляются (вводятся документами или балансовыми
  операциями).

## Дополнение после Этапа 7: 1С — многострочные документы

Раньше каждая строка файла 1С становилась отдельным документом с одной
строкой начисления, а один акт или УПД с несколькими позициями загрузить
было нельзя. Теперь:

- **Строки с одинаковым внешним ID 1С — один документ**, каждая строка
  файла — строка начисления со своей суммой, НДС и статьёй ОПиУ. Поля шапки
  (организация, контрагент, тип, направление, номер, даты, комментарий) можно
  заполнить только в первой строке документа, как часто выгружает 1С; если в
  двух строках одного документа они разные — документ не загружается, в
  протоколе указаны строки и поле («поле «дата» различается в строках 6 и 7»).
- **Аналитика строк** — новые необязательные колонки: содержание /
  номенклатура, подразделение, ЦФО, проект, продукт/услуга. Ищутся в
  справочниках по названию (ЦФО, проект, продукт — и по коду; проект — в
  организации документа); незнакомое значение — ошибка документа, а не
  тихо пустая аналитика. Мастер сопоставления узнаёт эти колонки по
  заголовкам сам.
- **Ошибка — на весь документ**: документ не загружается без части строк,
  остальные документы файла загружаются. Повторная загрузка по-прежнему
  идемпотентна и заменяет все строки документа — позиции, удалённые из
  документа в 1С, исчезают и здесь. Создание документа и его связи с 1С —
  одна транзакция (раньше два отдельных шага).
- Протокол считает документы и строки начисления: «документов создано 1,
  обновлено 2 (строк начисления: 5), ошибок 2». Шаблон файла содержит
  пример документа из двух строк и необязательные колонки. Файлы «одна
  строка — один документ» загружаются как раньше.
- Чистая логика группировки — `src/lib/integrations/onec-grouping.ts`,
  5 юнит-тестов.

Проверено через интерфейс: шаблон загружен как есть — 2 документа, 3 строки,
все 13 колонок сопоставлены автоматически. Затем файл CSV со своими
заголовками: документ из шаблона пришёл уже с тремя строками (проект найден
по коду «PA», услуга — по названию) и обновился, второй — обновился, новый УПД
создан, документ с разной датой в двух строках и документ с неизвестным
проектом отклонены с понятными сообщениями — «создано 1, обновлено 2 (строк
начисления: 5), ошибок 2». В базе у документа ровно три строки с нужной
аналитикой, контрагент по ИНН создан один раз. Тестовые данные удалены.

- **Не реализовано** (как и раньше): XML/JSON-выгрузки 1С — нужен реальный
  образец выгрузки конкретной конфигурации.

## Дополнение после Этапа 7: Битрикс24 — финансовый результат проекта

Раздел 11 ТЗ хочет видеть в Битрикс24 финансовый результат по сделке или
проекту, а в очередь уходили только статусы оплаты документов. Теперь:

- **Привязка**: в справочнике «Проекты» новое поле «ID сделки в Битрикс24»
  (уникальное — одна сделка = один проект).
- **Результат проекта** за всё время по проведённым документам — только то,
  что отнесено на проект напрямую (строки документов с этим проектом):
  выручка, прочие доходы, прямые расходы, прочие отнесённые расходы,
  валовая прибыль, результат, маржа. Общие косвенные расходы компании не
  распределяются — это допущение отчёта «Маржинальность», а не факт сделки.
  Денежная часть: получено от клиентов и осталось получить, оплачено
  поставщикам и осталось оплатить — оплата документа делится между
  проектами пропорционально их доле в его сумме.
- **Событие `project_financial_result`** ставится в очередь Битрикс24
  автоматически при проведении и отмене документа, сопоставлении и отмене
  сопоставления оплаты, импорте из 1С и автопроводке зарплаты — для проектов
  этого документа, привязанных к сделке. Ключ идемпотентности — хэш цифр:
  пока результат не изменился, новых событий нет. На странице Битрикс24 —
  таблица проектов со сделками с текущими цифрами и статусом последнего
  события и кнопка «Пересчитать и поставить в очередь изменившиеся
  результаты» (например, после привязки сделки). Отправка — тем же вебхуком
  и журналом, что и статусы оплаты.
- **Исправлена ошибка справочников**: при изменении записи очищенное
  необязательное поле не очищалось, а молча сохраняло старое значение (ИНН
  организации, код, ID сделки и т.д.) — побочный эффект исправления создания
  проекта. Теперь при изменении пустое поле записывается как «пусто», если
  колонка это допускает; обязательные в базе колонки (статус проекта)
  сохраняют значение. Новый тест сверяет все справочники со схемой: поле,
  необязательное в форме, должно допускать пустое значение в базе или иметь
  значение по умолчанию — иначе при сохранении была бы ошибка 500.
- Чистая логика — `src/lib/integrations/project-results.ts` (4 теста) и
  `src/lib/dictionaries/columns.ts` (5 тестов). Миграция
  `project_bitrix_deal`.

Проверено через интерфейс: проект «Внедрение СОУТ» привязан к сделке 1234
через форму справочника; акт на 300 000, из которых 200 000 — по проекту,
и расходы подрядчика 50 000. Страница Битрикс24: выручка 200 000, расходы
50 000, результат 150 000, маржа 75%, осталось получить 200 000; кнопка

встало в очередь само: получено 100 000 (две трети оплаты — доля проекта в
акте), осталось 100 000. ID сделки очищен через форму — в базе стал пустым,
статус проекта сохранился. Тестовые данные и события очереди (в том числе
оставшиеся от проверки импорта 1С) удалены.

- **Не реализовано**: реальная доставка в Битрикс24 по-прежнему не
  проверялась — нет доступа к порталу; формат события — наш JSON, его нужно
  будет сопоставить с полями сделки на стороне Битрикс24 (обработчик вебхука

## Дополнение после Этапа 7: финансовые сценарии — деньги с отсрочками и кредиты

Раньше остаток денег в прогнозе был «предыдущий + операционная прибыль −
платежи по кредитам»: вся выручка считалась полученной в месяц продажи,
поставщики — оплаченными сразу, а кредит был просто оттоком без процентов.
Теперь деньги считаются отдельно от прибыли:

- **Отсрочки оплаты** — два новых драйвера сценария по месяцам, в днях:
  «Отсрочка оплаты клиентов» и «Отсрочка оплаты поставщикам (переменные
  расходы)». Отсрочка в месяцах = дни / 30, дробная часть делит сумму между
  соседними месяцами: при 45 днях половина выручки приходит через месяц,
  половина — через два. Переменные расходы и комиссия посредников
  оплачиваются с отсрочкой поставщикам; постоянные расходы и ФОТ — в том же
  месяце. На прибыль отсрочки не влияют.
- **Старт прогноза** — фактический остаток денег (как и раньше) плюс
  фактическая дебиторка и кредиторка с зарплатой к выплате на сегодня (из
  управленческого баланса, с тем же ограничением видимости): считается, что
  они погасятся в первом месяце. Это меняет цифры существующих сценариев, если
  в системе есть непогашенные документы; в прогнозе это отдельные строки.
- **Кредиты — списком** в сценарии: сумма, месяц получения, ставка % годовых,
  срок, способ погашения (аннуитет, равными долями основного долга, проценты
  ежемесячно и долг в конце срока). Деньги приходят в месяц получения, платежи
  — со следующего; проценты (остаток × ставка / 12) — расход, уменьшают
  «Прибыль после процентов»; погашение основного долга — только отток денег.
  Копейки округляются, последний платёж закрывает долг ровно в ноль.
  Прежний драйвер остался как «Прочие платежи по кредитам/лизингу (вручную,
  без графика)».
- **Прогноз** показывает поступления от клиентов, оплаты поставщикам,
  погашение текущей дебиторки и кредиторки, получение и погашение кредитов,
  проценты, прибыль после процентов, дебиторку, кредиторку и долг на конец
  месяца; карточки — прибыль после процентов и долг на конец горизонта. То же
  — в выгрузке Excel и сравнении сценариев. Без отсрочек и кредитов прогноз
  считается как раньше (проверено прежними тестами).
- Чистая логика — `src/lib/financial-model/cash-timing.ts` (сдвиг по
  отсрочке, график кредита), `project.ts`, `loans.ts`; 16 новых
  юнит-тестов (в т.ч. аннуитет 1 200 000 под 12% на 12 месяцев — 106 618,55 в
  месяц). Таблица `FinancialScenarioLoan` (миграция `scenario_loans`).

Проверено через интерфейс: сценарий с октября 2026 — выручка 200 000 в месяц,
переменные 30%, постоянные 50 000, отсрочка клиентов 45 дней, поставщикам 30,
в системе неоплаченный акт на 40 000; кредит 1 200 000 под 12% на 12 месяцев
аннуитетом добавлен через форму. Деньги: октябрь 1 190 000, ноябрь
1 073 381,45, декабрь 1 056 762,90; прибыль после процентов в ноябре 78 000
(90 000 − 12 000); дебиторка 200 000 → 300 000; на конец горизонта остаток
денег 907 195,95 и долг 105 562,88 — всё совпало с ручным расчётом, в
сравнении сценариев и в Excel те же цифры. После удаления кредита через форму
остаток на конец — 880 000, прибыль после процентов равна операционной.
Тестовые данные удалены.

- **Не реализовано**: дебиторка и кредиторка на старте гасятся целиком в
  первом месяце, без учёта их собственных сроков оплаты; отсрочки задаются
  общими по сценарию, а не по клиентам или новым услугам; кредит без
  отсрочки платежей и досрочного погашения; налоги в прогнозе не считаются.
